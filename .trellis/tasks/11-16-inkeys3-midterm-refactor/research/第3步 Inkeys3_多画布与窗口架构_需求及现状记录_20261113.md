# Inkeys3 多画布、窗口与呈现体系：需求及现状记录

> **文档性质：需求与问题梳理（非架构定案、非实施方案）**  
> **整理日期：2026-11-13**  
> **涉及范围：** Inkeys3 / Draw3、白板与 `whiteboard3` 惯性拖动、桌面和 PPT 批注、板中板、多显示器、PDF／图片内容呈现、RTS／WM_POINTER／DirectManipulation（DM）、UInk 规范。  
> **状态标识：** **[现状]** 已知实现或既有约束；**[反馈]** 当前观察到的问题；**[需求]** 希望达到的能力；**[构想]** 尚未确认的实现方向；**[待确认]** 需要通过代码审查、实验或规范设计明确的内容。

## 0. 文档目的与边界

本文件用于记录 **Inkeys3 下一阶段可能进行的画布、输入、窗口与渲染系统调整的背景、需求和约束**，方便后续架构评估和开发规划。

需要强调：**目前尚未决定一定采用任何一套具体架构。** 之前讨论中的 `LogicalCanvas`、`CanvasView`、`WindowHost`、独立 Session、统一 GPU 提交线程、DComp Visual Tree，以及 UInk 1.1 的新类型等，都属于供比较的概念或候选方案，**不能视为已经批准的实现、命名或规范**。

本文件尽量描述“需要什么、为什么需要、现状有什么限制”，只在必要处记录用户已经提出的技术方向，不展开为强制执行的类结构、线程模型、API 设计或重构任务列表。

## 1. 背景与当前问题

### 1.1 Inkeys3 的现有绘制能力

- **[现状]** Inkeys3 使用 Draw3 负责主要墨迹绘制，Windows 图形管线主要包含 D3D11、D2D1.1；墨迹采用实时／活动／稳定等分层思路（常称 L0、L1、L2），还包括擦除、高亮等特殊合成语义。
- **[现状]** 主桌面批注目前有硬件 GPU 绘制路径，并存在为了特定窗口和兼容性场景使用的辅助前置表面、ULW 等机制。
- **[现状]** 开发目标仍包含 Windows 7 SP1 + Platform Update；并非所有现代 DXGI、DirectComposition、输入接口都能在最低系统上使用。
- **[现状]** 当前实现仍存在较多单画布／单产品 Host／单一窗口角色相关的假设；一些数据模型将画布内容、设备身份和 viewport 联系在一起。它们会影响后续多实例与共享内容能力。

### 1.2 白板惯性拖动与背景延迟

- **[反馈]** `whiteboard3` 相关开发中已经加入白板惯性拖动，但白板背景的**点阵、网格**在平移过程中存在明显跟随延迟、不够流畅的问题。
- **[需求]** 背景、墨迹及未来可能出现的 PDF／图片底图，应当在平移、惯性和缩放时保持一致，不出现肉眼可察觉的相对滑动或时间差。
- **[分析假设]** 目前怀疑背景与画布不属于同一个窗口／同一呈现链路，且背景使用 WARP，墨迹使用 Hardware GPU，是造成延迟的原因之一。
- **[现状线索]** 既有 `dev` 代码中，白板背景存在独立 UI 调度、绘制及窗口提交路径；Draw3 墨迹则由另一条帧循环处理。即使将背景也切换到硬件 GPU，只要相机采样、帧调度、缓存更新和最终提交不同步，仍可能有跟手问题。
- **[待确认]** `whiteboard3` 的具体提交方式、最新延迟来源、实际背景帧率与 CPU/GPU 耗时，目前**没有经过该分支最新源码的完整复核**。不得将上述假设当成已证实的唯一根因。

### 1.3 本次调整的动机不只是修复背景

希望一次性考虑以下长期场景，避免为解决当前的点阵问题引入只能应付单窗口的临时结构：

- 白板独立于桌面／PPT 批注运行，并可窗口化；
- 白板与 PPT 中都可以有“板中板”；
- 未来可能有 PDF 阅读器、图片查看器等画布内容；
- 同一个桌面或白板逻辑画布可能跨多个显示器呈现；
- 一个窗口可能同时显示不同的逻辑画布区域；
- 输入链路同时推进 RTS、WM_POINTER 和 DM 的适配；
- 性能、图形资源复用、多线程安全、Win7 兼容性以及 UInk 文件互通必须共同考虑。

## 2. 目标场景与功能需求

### 2.1 独立白板与窗口化白板

- **[需求]** 白板和桌面／PPT 批注应在内容、输入状态、交互行为等方面能够相对独立，而不是只能依赖同一个桌面批注画布。
- **[构想]** 白板可使用**普通、不透明、非分层 HWND**，直接由 GPU 渲染；不必继续把白板背景放入独立的透明／辅助前置窗口。
- **[需求]** 一个白板窗口可以同时承载底图（纯色、点阵、网格、PDF、图片等）与墨迹。显示 PDF 时，PDF 可以是**同一窗口内的底层内容**，而不需要再创建一个专门显示 PDF 的 HWND。
- **[需求]** 白板将来能够以全屏或窗口化形式出现，也能与其他批注界面并存。
- **[待确认]** 白板的窗口、逻辑画布、文档以及输入／渲染执行单元是否严格一一对应，尚未定案。

### 2.2 白板内板中板

- **[需求]** 同一个白板 HWND 内可以划出子区域，展示另一份**独立逻辑画布**，无需为每个子画布另开 HWND。
- **[需求]** 父、子画布可具有各自的背景、墨迹、视口和交互状态；子画布上的输入应进入正确的画布，不得误写到父画布。
- **[需求]** 子画布可透明或半透明，允许看到下层父画布的内容。例如背景半透明而子画布墨迹保持不透明；是否还支持整个子画布统一透明度，尚需明确。
- **[需求]** 父、子画布应保持正确裁剪、叠放顺序与命中测试；子画布的擦除不应误擦除父画布内容。
- **[范围约束]** 目前仅考虑**最多一层逻辑画布嵌套**，即父画布可以有子画布，但子画布内暂不继续嵌套孙画布。此限制不等于限制底图、墨迹等内部视觉层的数量。
- **[待确认]** 子画布区域应固定于窗口视口，还是固定于父画布世界坐标（随父画布平移），以及是否需要同时支持两种锚定方式。

### 2.3 桌面／PPT 场景中的板中板

- **[需求]** 除白板内部的板中板外，还希望在桌面批注层、特别是 PPT 放映场景下显示板中板。
- **[需求]** 桌面／PPT 板中板也需支持透明和半透明，能够与下方应用内容或已有批注叠加。
- **[需求]** 可以在板中板里绘制，也可以在板中板之外的桌面／PPT 批注层绘制；二者的笔迹、历史、输入归属不应混淆。
- **[待确认]** 桌面板中板最终采用独立浮动 HWND、同一 HWND 内的子 View，还是根据宿主和输入需要混合选择，目前不做强制决定。
- **[待确认]** PPT 内的子白板是跟随整个演示文稿，还是绑定某个稳定 SlideID 的页面；放映切换、恢复及保存时需要如何表达其宿主关系。

### 2.4 多显示器与跨屏连续笔迹

- **[需求]** 多个显示器可分别有覆盖自己屏幕的窗口和呈现目标，但它们可能属于**同一个桌面逻辑画布**，或者同一个需要跨屏显示的白板逻辑画布。
- **[需求]** 支持一份逻辑内容在多个窗口／显示视图中呈现，避免为每个屏幕复制一份语义上独立的墨迹。
- **[需求]** 例如鼠标绘制时跨过显示器边界，应在同一个连续世界坐标系中形成**一条笔迹对象**，而不是左屏和右屏各生成一半笔迹。
- **[需求]** 这条跨屏笔迹对应的记录、对象身份、撤销／重做等操作在逻辑上应连续；每个窗口只负责显示相应的可见部分。
- **[需求]** 每个显示器允许有自己的 HWND、交换链、局部裁剪与呈现频率；可能还会有自己的 RTS 或 WM_POINTER 输入入口。
- **[待确认]** 不同 DPI／缩放、不同刷新率、显示器负坐标、热插拔与重新排列时的逻辑坐标保存规则、物理笔宽策略。
- **[边界]** 两块触摸屏中产生的不同接触，不应仅因空间位置相邻而自动合并为同一笔；跨屏连续性首先针对**同一持续输入接触**。

### 2.5 多对多关系是核心需求

下面两种关系**需要同时支持**：

1. **一个逻辑画布在多个窗口中显示**：例如多个显示器共享桌面墨迹内容，同时使用各自可见区域与呈现资源。
2. **一个窗口中显示多个逻辑画布**：例如主白板 + 半透明子白板，在同一个 HWND 中最终合成。

这里的“画布逻辑”指具有内容和操作语义的画布，不等同于 HWND、交换链、GPU 纹理，也不一定等同于 UInk 1.0 中当前的 `Canvas` 块。

## 3. 图形呈现、版本兼容与性能约束

### 3.1 一个窗口尽可能承载完整内容

- **[构想]** 对白板而言，在**同一个 HWND 内**呈现底图、墨迹和板中板，减少多个窗口各自维护相机、帧调度和合成状态的复杂度。
- **[需求]** 白板拖动、缩放和惯性期间，背景与墨迹在视觉上保持同步，尽量避免每帧重复栅格化不变的背景内容。
- **[需求]** PDF、图片及图案底图允许缓存为 GPU 资源；相机运动时可以复用缓存，必要时异步提高可见区域清晰度。
- **[待确认]** 背景和墨迹是先合成到单张纹理，还是通过独立的图形／DComp 合成节点呈现；应以效果、复杂度及性能测试决定。

### 3.2 Win7 与 Win8+ 的初步方向

- **[构想] Windows 7 SP1：** 对普通不透明白板 HWND，采用传统 GPU 绘制和手动维护内部层级／合成，不强制使用 ULW。**但这不意味着透明桌面/PPT 叠加层在 Win7 也能完全取消 ULW 或其他兼容技术。**
- **[构想] Windows 8 及以上：** 考虑利用 DirectComposition 的 Visual Tree / Surface 缓存与变换能力，使背景和墨迹等内容能复用已绘制结果；无需为静态 PDF 的每次平移都重新栅格化 PDF 页面。
- **[需求]** 两套平台后端应尽可能拥有相同的用户可见行为；版本差异主要由呈现实现隐藏。
- **[待确认]** 现代 DComp 所需的具体接口最小系统版本、Win7 设备能力及回退路径、现有透明叠加窗口与 DComp 的关系，需按 API 和实际设备验证。

### 3.3 特别注意的合成语义

- **[约束]** Inkeys 的 L0／L1／L2、橡皮擦及高亮可能具有特殊 Add/Retain 等合成含义，不能简单把每个墨迹层当作普通 alpha 图层来合成。
- **[需求]** 擦除应只影响目标画布的墨迹；不应直接擦掉独立底图（PDF、图片、网格等），除非未来明确设计了可编辑媒体功能。
- **[需求]** 半透明子画布需要区分“**子背景透明**”与“**整个子画布透明**”，这两种合成数学意义不同。
- **[待确认]** DirectComposition 是最终负责多个 CanvasView 合成，还是仅用于已合成画布及底图的可视变换；Draw3 内部合成的边界尚未决定。

### 3.4 性能目标与资源压力

- **[需求]** 固定帧率的墨迹显示和输入消费应保持低延迟，不能因为 PDF 底图更新、子白板绘制或第二个显示器 Present 被整体拖慢。
- **[需求]** 尽量复用同一个 D3D11 设备和 Draw3 绘制能力，避免每新建一个窗口就完整复制昂贵的 shader、纹理及各种缓存。
- **[约束]** 独立 View 往往仍需独立的可变呈现状态与部分纹理，不能因为“共用同一个逻辑画布”就假定所有 GPU 缓存都能共享。
- **[待确认]** 多窗口 GPU 提交是否共用单一执行线程、是否使用 deferred contexts、每个窗口的绘制频率以及多交换链调度方式；**不得将并发 Draw3 绘制视为已确认可行**。
- **[待确认]** 单 View／多 View 显存预算、后台缓存和活动笔迹缓存的生存周期、隐藏窗口资源释放、低端核显／内存不足时的降级策略。

## 4. 输入链路与同步约束

### 4.1 既有输入路线

此前讨论的方向仍需保留在评估范围中：

- 教学大屏／一体机默认优先 RTS；
- Win8+ 笔记本默认倾向 WM_POINTER，并视设备和系统能力使用 DirectManipulation（DM）导航；
- 用户可以选择输入后端；
- Win10 及以下的 RTS 路径暂不引入 DM；Win11 + RTS 的新触控板适配作为能力探测／兼容路线；
- Down、Up、Cancel 等生命周期事件必须可靠保存；Move 可采取“保持最新状态”的策略，防止事件积压；
- Draw3 仍按照固定帧率消费输入，交给现有平滑／Ink Stroke Modeler 管线处理。

> 此处的 DM 是 **DirectManipulation**，主要用于触控／触摸板的平移、缩放及惯性导航，不是新的墨迹文件或画笔算法。

### 4.2 新场景引出的需求

- **[需求]** 一个窗口可命中不同逻辑画布；不同窗口也可把输入路由到同一逻辑画布。
- **[需求]** 每个接触在 Down 时有明确的目标画布，后续 Move 与 Up 不因跨越板中板或显示器边界而无意切换归属。
- **[需求]** 同一画布从多个窗口接收输入时，接触 ID 需要全局消歧；模型更新、历史修改顺序应确定。
- **[需求]** 独立白板与桌面批注允许同时活动，工具状态和操作历史不能相互污染。
- **[约束]** 由同一 HWND 提供多个子画布的情况下，不能简单为重叠区域重复注册多个 RTS 实例；应考虑输入区域路由。
- **[待确认]** 输入会话、窗口消息线程、RTS 线程、模型更新线程和 GPU 绘制线程如何分工，以及应当在哪一层保证唯一写入者和锁序。
- **[待确认]** 导航过程中触摸／笔输入与不断变化的相机如何进行时间和坐标对齐，特别是“一边惯性移动、一边落笔”。

## 5. UInk 现状与未来修改需求

### 5.1 UInk 1.0 当前表达了什么

根据公开的 UInk 1.0 Beta（`Header.version = 10`）规范：

- `Workspace` 用来描述通用批注、白板、PPT 及父子 Workspace／宿主关系；
- `Device` 用来描述物理显示面及父子 Window 显示区域，包括相对位置、大小和 `zIndex`；
- `Canvas` 绑定逻辑页面与对应的 Device，保存 viewport；后续 Ink、Shape、Media、Clear 归属于其作用域；
- 同一逻辑页面在多个 Device 上可以共享 `pageGuid`，分别拥有不同的 `viewport`；
- **但每个 Device 的 Canvas 拥有独立内容、独立 contentId 和 undoId。** 当前规范明确不把多屏墨迹或 Clear 历史作为同一份共享内容；
- Window Device **已经支持嵌套**，Workspace 也支持父子关系，不能简单认为 UInk 1.0 完全不支持板中板；真正缺失的是更明确的“共享内容、多 View 引用、跨屏连续同一笔”语义，以及完善的透明／锚定／输入关系描述。

### 5.2 UInk 1.0 当前缺失的关键能力

**[需求]** 新版本需要有办法表达：

1. 同一份逻辑画布内容在多个显示窗口／设备区域中呈现，而不是只共享页面 GUID。
2. 一条墨迹跨越屏幕边界，在文件中仍是一个连续对象，不必拆成每屏独立的笔迹与历史操作。
3. 一个窗口／Device 之内存在多个逻辑画布区域，具有独立的内容身份、视口、裁剪、层级和透明度。
4. 最多一层的父子画布关系，必要时包括父画布世界坐标／窗口视口坐标的锚定规则。
5. 桌面、白板和 PPT 宿主之间的保存、恢复与绑定关系；应继续遵守现有稳定 Page GUID／SlideID 语义。
6. 基础兼容应用依然可以理解简单画布，不能因为加入多视图而无条件要求所有软件实现复杂 UI 或多屏行为。

### 5.3 UInk 1.1 目前未定案的修改方向

- **[构想]** 在新版本中新增某种**共享逻辑画布／内容源**表达，再用独立的**视图绑定／显示映射**关联多个 Device 或 Window 区域。
- **[构想]** 可能新增一种 Canvas 类型、扩展现有 Canvas，或设计新的 View／Binding 结构；**具体类型名称、Type ID、字段、GUID 归属、内容流归属均尚未确定**。
- **[构想]** 继续利用已有 Workspace、Device、Page 结构，避免重复发明它们已经能表达的宿主与显示层级。
- **[构想]** 将基础单画布能力与 Inkeys 特有的高级墨迹／多视图能力按未来 Lite、Inkeys、Full 等兼容层区分；这些层级的最终定义仍需另行形成规范。
- **[需求]** 支持高兼容层向低兼容层的明确降级导出；旧版或第三方工具不能理解共享视图时，应有定义好的兼容投影／信息损失处理方法。
- **[约束]** 新版本不能靠旧读取器忽略未知字段，就假装共享历史和跨屏连续墨迹已经实现；规范版本和兼容声明必须与实际语义一致。

**注意：** 截至本次整理可核对的公开官网规范仓库，仍只有 UInk `version 10` Beta；尚未看到已公布并冻结的 UInk 1.1 新 Canvas 类型。本节全部属于**未来标准需求与候选方向**，不应在后续引用时描述为“1.1 已经规定”。

### 5.4 运行时模型与文件格式的关系

**[现状]** 可见 `dev` 的 `Draw3.InkDocument.cppm` 中，`InkCanvas` 同时含 `DeviceKey`、`InkViewport` 和 Stroke 集合，`InkPage` 以 DeviceKey 查找 Canvas，且当前 viewport 实现对缩放仍有限制。

**[需求]** 如果以后让一份逻辑内容出现在多个显示窗口，运行时和序列化层都需要能表达共享内容，不应只有 UInk 格式支持，运行时依旧按设备复制墨迹；反过来也不应只有运行时共享，保存时丢失这一身份关系。

源代码参考：[Draw3.InkDocument.cppm（dev）](https://github.com/Alan-CRL/Inkeys/blob/dev/Inkeys/Inkeys/Drawing/Draw3/Draw3.InkDocument.cppm)。

## 7. 希望验证的典型行为（不是已定的测试实现）

1. 白板惯性平移时，网格／点阵与墨迹视觉同步；未来 PDF 底图也不出现明显拖尾。
2. 普通白板窗口显示 PDF 页面与墨迹，底图无需额外 HWND；快速平移可使用已有缓存。
3. 同一白板 HWND 内出现半透明子白板，父子各自能写、擦、切换工具，并能正确命中和裁剪。
4. PPT 上出现透明板中板，在板内写字与板外对 PPT 批注互不串写。
5. 两个显示器上拖动鼠标画过边界，只产生一条连续的逻辑墨迹和一次对应的历史操作。
6. 在独立白板绘制的同时，桌面批注仍可继续响应；较慢的呈现目标不应无条件阻塞所有窗口。
7. 混合 DPI、不同刷新率及显示器插拔不会使已有笔迹突然跳位或丢失。
8. 保存、恢复和跨版本导出能够保留或明确降级画布、子板、宿主与共享内容关系。
9. Windows 7 SP1 能继续提供可接受的功能回退，而不是由于现代 DComp／DM 能力缺失而不能使用基本白板或批注。

- **UInk 公开规范：** 上述 UInk 仓库源文件为当前公开的 1.0 Beta 版本说明；与后续尚未公布的 1.1 草案必须分开引用。
- **Windows 能力：** 本文只记录计划支持的系统族和大体后端方向；最终的 API 版本支持、Win7 Platform Update 能力和应用兼容性需要在实施前逐项核验。

## 9. 暂定结论

当前最重要的需求并非某一个已选定的新类或渲染技巧，而是以下几个**可独立验证的目标**：

- **一个窗口承载多份逻辑画布**，支持最多一层板中板、独立输入与透明合成；
- **一份逻辑画布呈现在多个窗口**，支持多显示器中的同一笔连续墨迹及统一内容身份；
- **背景、媒体、墨迹在同一视图中保持视觉同步**，避免惯性拖动时的延迟和重复背景绘制；
- **保留低版本 Windows、不同输入后端和有限硬件资源的适配空间**；
- **推动 UInk 的内容与显示关系解耦**，但不提前把未来的具体版本结构当成已发布规范。

**后续设计评审应围绕这些目标比较方案，而不是默认前面讨论过的任何对象拆分、线程组织或 UInk 新类型已经得到确认。**
