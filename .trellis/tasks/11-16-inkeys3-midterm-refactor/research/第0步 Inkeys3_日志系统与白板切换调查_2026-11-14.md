## 一、摘要与决策

1. **保留 spdlog 1.17.0，不建议现在换版本。** Inkeys 的 `vcpkg.json` 固定 `spdlog 1.17.0`，当前 baseline 对应 `spdlog 1.17.0#0 + fmt 12.1.0`。调查时 vcpkg 主分支已出现 port `1.17.0#1`，主要回补格式字符串 API 兼容补丁；`#1` 是 vcpkg port 修订号，并非新上游版本。一次只改变一个变量，避免日志重构同时升级整个依赖集。
2. **现有 spdlog 主要性能风险在配置和用法。** 异步池是 `8192` 队列项、**64 worker**；一个共享文件 sink 受互斥锁保护，多 worker 不能让文件并行写入，且会增加竞争与日志重排风险。建议以 **1 worker** 起步测试。
3. **统一日志不能仅把 `stdout` 改为 spdlog。** 当前 `IDTLogger`、`UI3Diagnostics`、`Draw3::DiagnosticOutput`、C++ / C# PPT 日志、CrashHandler 输出路径分散；部分诊断在没有控制台或调试器时根本不启用。
4. **白板切换弹窗不是确定的 Win32 API 错误。** 它表示工作区事务累计 **4 次失败预算**后停止重试。预算跨阶段累计，可能因为原生命令失败、执行超时、目标画布状态长期不满足、白板背景未就绪或最终背景核验未通过等原因消耗。
5. **目前几处故障信息丢失是确定的。** `FailWorkspaceRequest()` 没有传失败原因；工作区回执没有暴露底层保留的 native / rollback 错误；白板 RenderBackground 把多种 HRESULT 和 ULW 问题折叠成 `Retry`；`catch (...)` 还可能将非内存错误记录为内存不足。
6. **C# 可以进入同一个文件日志。** 推荐通过进程内 COM 扩展接口 / 回调交给 C++ 的唯一文件日志写入者，不需要更换 .NET Framework 4.0 或引入 IPC；回调不可用时保留受控 fallback。
7. **执行顺序**：先修白板失败诊断闭环 → 再重构统一日志基座 → 再迁移 Draw3 与 C# → 最后完整性能与 Win7 回归。

### 3.2 主 logger 的原始配置

```cpp
// 当前代码（不是推荐配置）
auto sink = std::make_shared<spdlog::sinks::basic_file_sink<std::mutex>>(
    globalPath + L"log\\idt" + Timestamp + L".log", true);
spdlog::init_thread_pool(8192, 64);
IDTLogger = std::make_shared<spdlog::async_logger>(
    "IDTLogger", sink, spdlog::thread_pool(),
    spdlog::async_overflow_policy::block);
IDTLogger->set_level(spdlog::level::info);
IDTLogger->set_pattern("[%l][%H:%M:%S.%e]%v");
IDTLogger->flush_on(spdlog::level::info);
```

【已确认】主日志在 EXE 所在目录的 `log/idt<时间戳>.log`；启动时尝试清理约 7 天前或目录超过 10 MiB 时的历史日志。清理直接遍历，没有保证按最旧优先；当前会话日志没有大小轮转，历史清理也只在启动时发生。日志初始化没有完整的文件不可写/创建失败回退链。

【建议】先试 `init_thread_pool(8192, 1)`；UI3 和主日志共享一个受控 sink；增加单文件大小轮转与总保留配额；`flush_on(err)` 并配置周期性 flush。异步 `flush()` 只能表示已提交 flush 请求，不能保证调用返回时已经物理落盘。普通业务日志可走可靠通道，但不能让 Draw3 高频绘制/输入线程直接执行可能 `block` 的写入。**所有数值都需要在实机高负载下验证。**

还要注意：当前主 logger 是手工构造的；直接写 `spdlog::info()` 不一定指向 `IDTLogger`，`spdlog::flush_every()` 也要求考虑注册关系，推荐统一通过 Inkeys 自身的日志接口访问。

### 3.3 Draw3 专项输出的保留与迁移

【已确认】`Draw3::DiagnosticOutput` 采用非阻塞入队（try-lock），定长队列约 **1024 条**、记录最大约 **4096 字节**，有丢弃计数、后台消费及有界退出，且考虑了 `GetLastError()` 的保护。这些机制是为了保护渲染线程，**不应该直接以主 logger 的阻塞策略取代**。

另外，[`Session::Start()` / `Available()`](https://github.com/Alan-CRL/Inkeys/blob/215184d4e096f262b8b4bf11471cb5b14fa53884/Inkeys/Inkeys/Drawing/Draw3/Draw3.DiagnosticOutput.cpp#L271-L358) 当前按 stdout / stderr / 调试器存在与否决定可用性。仅把后台 `WriteRecord()` 改为 spdlog，不会让无控制台的普通用户自动获得日志。

【建议】拆分两个概念：**文件日志采集是否开启** 和 **控制台/调试器镜像是否开启**；继续使用非阻塞采集，消费线程输出至统一日志 sink。事件发生时立刻保留原始时间戳和线程 ID；不能用转发线程 ID 代替。Debug / Trace 输出按事件变化、抽样、频率限制，避免逐帧刷日志。

补充：现有日志仍有异常处理、图形恢复、退出保存失败等有价值的事件，迁移时须按错误语义重新分配日志等级，不能简单把 stdout 视为 Info、stderr 视为 Error。

## 四、桌面 → 白板切换失败：状态机与日志缺口

### 4.1 弹窗代表什么

当前中文提示：

> 白板窗口切换未完成，已停止自动重试。可再次点击主栏的白板按钮取消本次切换，或前往设置的绘图页重试。

来源：[`zh-CN.jsonc`](https://github.com/Alan-CRL/Inkeys/blob/215184d4e096f262b8b4bf11471cb5b14fa53884/Inkeys/src/i18n/zh-CN.jsonc#L181-L186)、[`Setting.cpp` 弹窗入队](https://github.com/Alan-CRL/Inkeys/blob/215184d4e096f262b8b4bf11471cb5b14fa53884/Inkeys/Inkeys/UI/Setting/Setting.cpp#L5603-L5619)。这类通知也用于退出白板、桌面/放映工作区切换未完成。**看到提示并不能直接判定 GPU、窗口 API 或白板背景哪一个出错。**

可概括为以下步骤：

```text
发布 workspace 意图/revision，抑制切换期间新输入
  -> 准备 UI / Product 的目标状态
  -> RequestPrepareWorkspaceWindowPolicy + native receipt
  -> WorkspaceTargetReady（Draw3/尺寸/内容/工具与输出）
  -> PublishActive + RenderBackground + BackgroundPrepared
  -> RequestCompleteWorkspaceWindowPolicy + native receipt
  -> BackgroundMatchesActive + 最终身份核验
  -> CommitWorkspaceHandoffLocked
  -> 提交 Bar、Freeze、工具、输入状态
```

主流程：[`IdtState.cpp` #L3930-L4134](https://github.com/Alan-CRL/Inkeys/blob/215184d4e096f262b8b4bf11471cb5b14fa53884/Inkeys/IdtState.cpp#L3930-L4134)。

### 4.2 累计失败四次的精确含义

在 [`WorkspaceHandoff::Fail()`](https://github.com/Alan-CRL/Inkeys/blob/215184d4e096f262b8b4bf11471cb5b14fa53884/Inkeys/IdtState.cpp#L215-L354) 中：

```cpp
if (++failures >= 4) { failed = true; return true; }
retryAt = now + std::chrono::milliseconds(250U << (failures - 1));
```

- 同一次请求 `revision` 的失败次数在**不同阶段之间累计**；正常状态进展不会自动清空计数。
- 第一次、第二次、第三次失败后的退避依次为 **250 ms、500 ms、1000 ms**；第四次结束自动重试。
- `WorkspaceWaitTracker::Stalled()`：在阶段及所跟踪的输出 revision、内容 revision、presentation identity、背景 revision、背景 ready 状态都没有进展的情况下，以 **250 ms** 为一次无进展判定预算。这并不是 GPU 整体完全停顿的证据。
- `WorkspaceNativeOperation::NoteExecutingTimeout()`：原生命令入队后 **1500 ms** 仍在执行，才有超时故障处理；纯排队过期与取消语义应同真实 API 故障区分。
- 等待阶段包括 `BackgroundInactive`、`TargetReady`、`BackgroundPrepared`、`FinalBackgroundActive`。Prepare/Complete 命令本身也可失败；因此“四次”并不等于“同一个系统调用失败四次”。

**重要规则：**

- 对 Win32 API：失败后在**同一线程、紧邻失败调用**处获取 `GetLastError()`；后续调用和跨线程转发可能覆盖它。
- 对 HRESULT：记录出错 API 名称和真实 HRESULT（建议 `0x{:08X}`），不要用后续 `GetLastError()` 替代。
- 资源/所有权/identity 不匹配属于**应用内部原因码**，不能伪造 Win32 错误。
- 原生执行错误与回滚错误应并存，并保留第一个失败原因。
- `Cancelled`、`Expired`、`Rejected`、执行超时与真实 API 返回失败应有不同枚举。

### 4.4 `WorkspaceTargetReady(false)` 要告诉我们“哪项没准备好”

[`WorkspaceTargetReady`](https://github.com/Alan-CRL/Inkeys/blob/215184d4e096f262b8b4bf11471cb5b14fa53884/Inkeys/IdtState.cpp#L653-L716) 的条件包括：

- Draw3 Host `running` / `consumerFatal` / host generation / recovery；
- 白板加载状态；
- 画布提交大小和目标窗口大小；
- first frame / presentation UI ready / output revision；
- content revision 与 presented content revision；
- applied product revision、当前工具、选择模式等。

【建议】把现有同一次 ready 判断扩展成 `ReadyResult { ready, blockers, expected, observed }`，返回“不满足的条件集合”，避免新写一套与核心判定逻辑可能不一致的诊断程序。

假设日志示例（**不是当前已经输出的日志**）：

```text
WARN event=workspace.wait session=7F3A revision=85 stage=TargetReady
     blockers=content_not_presented,tool_not_applied
     expected_content=78 presented_content=77
     expected_tool=HardPen applied_tool=Selection stalled_ms=250
```

### 4.5 建议采用的结构化事件模型

关联键建议直接使用 **`sessionId + workspaceRevision`**，不必再创造一套相互独立的工作区业务编号。每个 native 命令可有额外 `nativeCommandId`。

| 字段 | 含义 |
| --- | --- |
| `timestamp`, `steadyElapsedMs`, `threadId` | 原始发生时间、事务耗时和**产生事件**的线程 ID |
| `sessionId`, `workspaceRevision` | 启动身份 + 工作区请求版本 |
| `from`, `to`, `minimized` | 来源与目标工作区、最小化状态 |
| `stage`, `reason`, `blockers` | 当前阶段、失败原因、未满足条件集 |
| `nativeCommandId`, `nativePhase` | 哪一次命令、Queued/Executing/Committed/Rejected/Cancelled/Expired |
| `api`, `hresult`, `win32Error` | 仅当实际存在系统错误时填充 |
| `rollbackError`, `rollbackStatus` | 回滚的原始原因与恢复责任 |
| `firstFailure`, `latestFailure` | 第一个真实故障及最终停止原因都要保留 |
| `failureCount`, `retryDelayMs`, `stalledMs` | 消耗预算、退避时间、无进展时间 |
| `hostGeneration`, `productRevision`, `outputRevision`, `contentRevision` | 必要的状态身份及期望/实际值 |

建议定义事件名：

```text
workspace.request
workspace.prepare_native
workspace.wait
whiteboard.resources_failed
whiteboard.present_failed
whiteboard.receipt_failed
workspace.complete_native
workspace.attempt_failed
workspace.failed
workspace.rollback_failed
workspace.recovered
workspace.completed
workspace.cancelled
workspace.retry_requested
```

**日志节流规则**：状态进入/离开、原因变化、到达无进展阈值、失败重试及最终结果要记录；同一等待状态不要每帧重复记录。最终 `workspace.failed` 应包含失败最初起因、最终起因、累计次数、回滚状态和关联 ID；用户弹窗可以提供短诊断编号用于匹配日志，但不要直接向用户展示内部 HRESULT 堆栈。

## 五、C# PptCOM 的统一日志方案

### 5.1 当前事实

- `PptCOM` 目前是 Inkeys 内进程 COM 对象，外部 PowerPoint/WPS 自身运行在哪个进程，不影响这个结论；C++ 创建 COM 对象并传递原生状态接口。参考 [`IdtPlug-in.cpp`](https://github.com/Alan-CRL/Inkeys/blob/215184d4e096f262b8b4bf11471cb5b14fa53884/Inkeys/IdtPlug-in.cpp#L366-L417)。
- [`SetConsoleOutputEnabled(false)`](https://github.com/Alan-CRL/Inkeys/blob/215184d4e096f262b8b4bf11471cb5b14fa53884/PptCOM/PptCOM.cs#L238-L257) 将 `Console.Out` 和 `Console.Error` 指向 `TextWriter.Null`；普通 C# 消息不等于自动进文件。
- C# [`PptPerfTrace`](https://github.com/Alan-CRL/Inkeys/blob/215184d4e096f262b8b4bf11471cb5b14fa53884/PptCOM/PptPerfTrace.cs#L113-L141) 直接 `Console.OpenStandardError()`，只重定向 `Console.SetError()` 还不够。
- [`ExecuteOwnerCommandCore()`](https://github.com/Alan-CRL/Inkeys/blob/215184d4e096f262b8b4bf11471cb5b14fa53884/PptCOM/PptCOM.cs#L1853-L1910) 存在 `catch { return -1; }`，异常在最有用的现场被吃掉，必须在返回前保留异常类型、HRESULT、阶段；现有“busy COM”等可恢复语义必须保持不变。
- [`IdtPlug-in.cpp` 中 HRESULT 格式拼接](https://github.com/Alan-CRL/Inkeys/blob/215184d4e096f262b8b4bf11471cb5b14fa53884/Inkeys/IdtPlug-in.cpp#L380-L423) 有 `L" (0x" + std::to_wstring(err.Error()) + L")"`，`std::to_wstring()` 实际输出十进制，前缀 `0x` 并不能将其变成十六进制，应改为真正的 8 位十六进制。

### 5.2 推荐设计

```text
C# PptCOM / ManagedLog
    |  新增 COM 扩展接口注册函数指针、或安全的原生回调句柄
    v
C++ LogBridge（边界验证、复制消息、保留事件原始时间/线程、异常隔离）
    |
    v
Inkeys LogService（统一等级、事件字段、文件队列）
    |
    v
spdlog 统一文件 sink（唯一文件写入者）
```

- C# 不需要、也不应分别实例化 spdlog 或两个互不知晓的 rolling file logger 后同时写相同文件。
- 使用**新的 COM 扩展接口**（例如 `QueryInterface` 获取）而非破坏原接口 ABI；.NET Framework 4.0 支持 `Marshal.GetDelegateForFunctionPointer(IntPtr, Type)` 的非泛型重载。明确传参长度、编码 UTF-8/UTF-16、调用约定和线程安全。
- 原生回调仅做受控数据复制/入队，不重入 Office COM，不同步等待 UI；原生服务关闭前需撤销回调、处理 delegate 生命周期，禁止 dangling pointer。
- 注入前、注入失败、退出晚期时保留 console/stderr/紧急 fallback，不让日志函数异常破坏 COM 原始错误信息或业务返回值。
- `PptPerfTrace` 按独立入口迁移，不指望 Console 重定向捕获；若将来 PptCOM 改成独立 EXE，再考虑进程间统一收集。

## 六、日志重构实施建议（分阶段）

### P0：优先修白板切换失败，暂不做大架构重排

- [ ] 统一失败结果 `WorkspaceFailureDetail`：阶段、原因、首次原因、最新原因、重试计数、elapsed、关键身份。
- [ ] 将 `FailWorkspaceRequest(revision)` 扩展为携带真实失败上下文；最终停重试一定写 `Error`。
- [ ] 每次失败预算消耗写 `Warn`；等待阶段进入/变化写节流的 `Debug`。
- [ ] `WorkspaceWindowReceipt` 传出 native error / rollback error / 失败子步骤；Prepare/Complete 补完整诊断。
- [ ] 白板 `EnsureDeviceResources`、`GetDC`、`ReleaseDC`、`EndFrameDraw` 失败处就地保存 HRESULT。
- [ ] `SubmitFreezeSurface()` 将输入无效、ownership mismatch 与真正 ULW 失败区分；紧贴 `UpdateLayeredWindowIndirect()` 的失败捕获 `GetLastError()`。
- [ ] 修正捕获任意异常就记录 `ERROR_NOT_ENOUGH_MEMORY` 的误分类。
- [ ] `WorkspaceTargetReady` 返回 blockers 与必要的 expected/observed；不复制第二套 ready 判断逻辑。
- [ ] `workspace.completed` / `workspace.cancelled` / `workspace.recovered` 覆盖成功、主动取消和恢复完成，避免误报持续失败。

### P1：日志基座重构

- [ ] 统一初始化/销毁顺序：启动前缓冲、运行期服务、退出后备与 CrashHandler 分工。
- [ ] `8192 / 64` 从 1 个 worker 起对照测试；不改 Draw3 热路径的非阻塞要求。
- [ ] 调整 flush 策略，并为关键错误 / flush / 终止处理提供可靠语义。
- [ ] 运行期文件大小轮转、按时间清理/空间预算、目录失败时后备路径。
- [ ] 文件采集、控制台显示、Debug/Trace 采样三个开关彼此独立。
- [ ] 日志级别与事件格式统一，避免 `spdlog::info()` 走到错误的默认 logger。
- [ ] MSIX 安装版日志放用户可写位置；便携版保留合理的便携目录策略及不可写回退。

### P2：迁移 Draw3 与 C# 旧输出

- [ ] Draw3 保留非阻塞队列、丢弃统计、原始发生时间/线程 ID，交给统一日志消费。
- [ ] 审查所有 `DiagnosticOutput` 的真实等级；把图形恢复、保存失败等关键内容强制纳入普通日志。
- [ ] C# 增加 `ManagedLog`，通过安全 COM 扩展/原生回调接线；注册失败时 fallback。
- [ ] 修正 C# `catch { return -1; }` 等信息丢失处，但不改变公开业务返回码。
- [ ] 单独迁移 `PptPerfTrace`；修复 C++ HRESULT 的“假十六进制”。
- [ ] 不改变现有测试工具的 PASS/FAIL 输出协议；保留 crash dump 独立通道。

### P3：完整验证与回归

- [ ] Windows 7 SP1 + KB2670838：二进制加载、文件/轮转、字体/中文路径、ULW 背景、C# COM 日志。
- [ ] Windows 10 / 11：DComp / ULW 切换、正常桌面→白板→桌面、快速重复切换、最小化/恢复、PPT 工作区切换。
- [ ] 故障注入：candidate receipt 过期、native Rejected、ownership mismatch、ULW 失败、D2D device lost、TargetReady 不满足、`1500ms` native executing timeout、`250ms` 无进展。
- [ ] 验证同一请求连续多阶段计数时，最终日志**同时保留第一个底层原因与停止原因**。
- [ ] 关闭控制台 / 无调试器的用户模式能否导出全部关键日志；检查异常退出后仍能定位最近状态。

- [ ] C# COM busy、翻页失败、事件绑定失败、退出保存屏障失败、日志回调关闭时的安全性。
- [ ] 输出中不要默认包含用户文档正文、文件内容、敏感地址、Office 文档标题或用户标识；提供可分享的故障诊断日志。

## 七、最终验收标准
