# Inkeys3：基于 Magnification API + OpenCV 的通用滚动批注初版

## 0. 任务目标与总要求

请在当前 `Alan-CRL/Inkeys` 仓库的 **dev 分支**中，分阶段实现一项新功能：**视图调整（滚动批注）**。

功能目标：

用户已经在桌面画布上绘制了墨迹，点击主栏新增的“视图调整”按钮后：

1. Inkeys 先通过现有 Magnification API 截取一帧不包含 Inkeys 自身窗口的底层画面，初始化 OpenCV 视觉追踪器。
2. 初始化成功后，绘图画布进入穿透状态，但墨迹保持可见，主栏仍然可以交互。
3. 用户通过手指、触控笔、鼠标、触控板、滚轮等正常操作下层应用，例如 Edge、Chrome、Word、PDF 阅读器。
4. Inkeys 持续获取底层画面，通过 OpenCV 追踪实际内容的位移，使已有墨迹同步移动。
5. 原始墨迹保持在统一的 Canvas 内容坐标系中，不直接修改所有 Stroke 的点坐标。
6. 在追踪过程中持续补充新的特征点，支持长距离连续滚动。
7. 持续计算跟踪可信度。如果截取到全黑/无效画面、匹配失效或可信度不足，则暂停进一步更新内容位置。
8. 用户再次点击按钮，结束视图调整，恢复绘制。原有墨迹、继续书写的墨迹、撤回和 UInk 保存恢复仍然要正确。

这项功能采用**主动切换穿透模式**，不需要 Inkeys 拦截和重新注入多指手势。下层应用正常处理自己的平移、滚动、边界和惯性。

### 本次范围

- 优先实现桌面 Desktop 画布中的单一内容区域跟踪。
- 初版仅支持二维平移，不实现缩放、旋转或非刚性内容变换。
- 不做浏览器扩展、Word COM、UI Automation。
- 不做丢失后的自动恢复、手动重新定位。
- 不做悬浮文字提示、复杂用户引导或正式设置页面。
- 不改变现有墨迹算法、Shader、实时预测、笔锋或渲染参数。
- 不要求这项新功能兼容 Windows 7；可按实际依赖设置 Windows 8.1 或更高版本门禁，但绝不能提高整个 Inkeys 的最低系统版本。
- 后续会研究自动恢复、手动校准、语义锚点、不同运动区域、缩放和更完善的交互，因此需要保留扩展空间。

所有修改都应遵守仓库 `AGENTS.md`、`.trellis` 规范。坚持最小化修改，不做无关重构，保持原始文件编码、BOM 和 CRLF/LF 换行方式；关键逻辑适当编写简洁中文注释。

**请先调查，再逐阶段实现。每个阶段完成后执行可用的验证并记录结果，继续下一阶段。不要仅输出计划就结束任务。**

## 第二阶段：Magnification API 持续截图 PoC

先实现独立可测试的截图服务，不接入正式滚动批注。

建议使用类似 `MagCaptureService` 的职责划分，但命名和文件布局遵循现有项目规范。

### 功能

1. 按需启动一次 Capture Session。
2. 确定主显示器上的追踪区域，第一版可以只支持主显示器。
3. 更新 Mag 的 Exclude Filter，确保不包含 Inkeys 画布、主栏、定格窗口等。
4. 在不向用户显示捕获窗口内容的情况下，通过 `PrintWindow(PW_RENDERFULLCONTENT)` 获取 Mag Child 画面。
5. 输出 BGRA 或其他明确格式的 CPU 图像缓冲区，供后面的 OpenCV 使用。
6. 提供图像宽高、Stride、Source Rect、采样时间戳和递增序列号。
7. 支持连续截图，而不是只获得一张静态图像。
8. 正确处理初始化失败、窗口销毁、停止会话、重复启停和资源释放。

Mag 截图及 PrintWindow 不得运行在主栏 UI 或 Draw3 实时绘制线程。

优先使用现有 DIB 资源管理方式，避免每帧反复创建大块位图。

暂时可以采用 15–30 FPS 的初始采集目标，实际频率根据耗时测试决定，不要承诺恒定帧率，也不能无界积压截图。

### 截图有效性检测

这部分必须在初版中实现：

- API 调用返回失败。
- 图像尺寸为零、不正确或者像素缓冲无效。
- 捕获到几乎全黑、纯黑或缺乏有效信息的画面。
- 图像颜色/亮度异常，无法生成足够的视觉特征。
- 捕获长时间没有产生新结果。

全黑识别建议结合灰度均值、方差、近黑像素比例判断，不应把正常的暗色主题页面全部误判成黑屏。

另外，**连续多张图像完全相同并不一定是错误**，也可能是用户没有滚动。不能单凭图片 Hash 相同就判定截图失败。

失败时给出明确原因代码，并提供控制台日志。不需要做正式 UI 提示。

### 验收

验证静止画面、浏览器滚动、窗口不显示、Inkeys 自身窗口排除和连续启停。

如果隐藏状态下无法连续得到真实更新的画面，必须如实报告，并在 Mag 方案内调查原因；不要未经分析就私自更换为 Desktop Duplication 或 Windows.Graphics.Capture。

## 第三阶段：OpenCV 位移跟踪、可信度与特征接力

建立独立 `VisualMotionTracker`。它只处理输入图像，不知道 HWND、Draw3、UInk 或主栏按钮。

### A. 初始化

在进入穿透前获取有效基准帧 F0。

对图像进行：

- 必要的裁剪和降采样。
- 灰度转换。
- `cv::goodFeaturesToTrack()` 角点提取。
- 以分块/网格方式保证角点空间分布。
- 初始化第一批追踪特征点。

可以先从 200–500 个特征点、半分辨率图像开始实验，最终数值依据性能调整。

如果基准帧为全黑、角点严重不足、无效区域过大，则初始化失败，不能进入 Tracking 状态。

### B. 连续跟踪

使用：

- `cv::calcOpticalFlowPyrLK()`
- Forward-Backward Check
- 位移中位数、RANSAC 或其他鲁棒估计方法

估计相邻画面中**主要内容区域的真实平移**。

不要直接根据双指移动量、滚动指令或鼠标滚轮增量修改画布坐标。

必须正确处理：

- 正常向上/向下滚动。
- 反向滚动。
- 水平滚动。
- 页面遇到滚动边界，实际位移为零。
- 手指抬起后目标程序仍在惯性滚动。
- 图像中存在少量动态内容或静止 UI。

第一版采用主要内容区域的二维平移模型。

如果检测到不能用单一平移解释的显著缩放、旋转或布局变化，应降低可信度，不要把异常运动当作普通平移写入画布。

### C. 特征点接力

不能始终依赖 F0 的特征，因为长距离滚动后这些点会离开屏幕。

请实现：

1. 追踪成功后保留仍然有效的旧点。
2. 监控有效特征数量和空间分布。
3. 在点数下降或某些区域缺少特征时，补充新角点。
4. 新角点根据当前**已确定的累计坐标变换**获得其内容坐标。
5. 旧点移出屏幕后可以删除。
6. 新旧特征共同完成接力，持续跟踪长距离滚动。

不要把每次新特征提取都理解为“重新以当前截图为世界坐标原点”。

始终维护累计内容变换，例如：

`T_current = T_frame_delta × T_previous`

仅当当前帧已经通过可信度检查时，才允许更新累计变换和进行特征接力。

### D. 跟踪可信度

每帧输出可信度（0–1），应结合至少以下指标：

- 有效特征点数量。
- Forward-Backward Check 通过情况。
- 鲁棒估计的内点比例。
- 中位数残差或重投影误差。
- 特征分布覆盖率。
- 本帧是否存在不合理的位移跳变。
- 图像捕获本身是否有效。

可以将最低有效特征约 40、内点比例约 60%–65%、残差约 1–2 个处理像素作为实验起点，不要求使用固定的最终阈值。

特别注意：

**高可信度的零位移应当被接受，而不是被判定为跟踪失败。**

如果可信度低于阈值，应拒绝该帧的位移，不得将错误变换写入累计坐标。

本次初版可以在持续不可信或明确严重失效时进入 `Paused` 状态：

- 保留最后一次可信变换。
- 停止继续移动墨迹。
- 不自动恢复。
- 不进行手动重新定位。
- 用户仍可以通过原来的按钮退出。

如果发生一次明显严重的无效捕获（例如全黑、无有效帧），可以立即暂停；对于普通短时跟踪波动，可以使用少量连续失败帧门限，避免偶发噪声导致整个会话停止。

### E. 离线测试

请制作可重复的测试或小型诊断工具，至少包含：

- 已知像素位移的平移图像序列。
- 不移动的静态图像。
- 全黑和近乎纯色的无效图像。
- 连续多个屏幕距离的长滚动序列。
- 原有特征离屏、新特征接力的场景。
- 正向滚动后反向滚动。
- 少量固定工具栏、动态内容干扰。
- 特征匹配不足导致暂停。

输出累计位置与预期位置的误差。

第一阶段使用合成图像即可，随后再测试真实浏览器连续截图。

## 第四阶段：正式接入 Draw3 平移及主栏交互

### A. 新增主栏按钮

名称暂定 **“视图调整”**。

根据现有主栏扩展按钮注册体系添加，优先放在合理的扩展位置，不随意修改主栏的固定分区和尺寸规则。

最初只要求：

- 一个按钮。
- 启用、关闭两个状态。
- 简单且明确的选中视觉反馈。
- 必要的 i18n 和 SVG 资源。
- 不创建复杂菜单和提示文本。

建议默认只在 Desktop 工作区开放。

### B. 启用时序

严格采用：

1. 用户点击按钮。
2. 检查当前工作区和绘制状态，处理正在进行的输入生命周期。
3. 启动截图服务。
4. 获得 F0 并通过有效性检查。
5. 初始化 OpenCV Tracker，确认有足够特征。
6. 使用现有 Window Service 设置画布穿透。
7. 状态切换为 Tracking，主栏保持可交互。
8. 连续捕获、计算真实内容位移、发布已确认变换。

如果第 3–6 步任意失败，应完整回滚资源与窗口状态，仍保持原来的正常绘制能力。

需要注意当前可能存在 Drawpad 和 DrawpadPresentation 两个 HWND，务必根据现有窗口策略确定需要修改哪些角色。

不要只修改某一个窗口后，让输入仍然被另一张不可见或透明画布截获。

### C. 墨迹跟随

这里优先调查并复用现有 `CanvasCommandType::TranslateViewport` 与 Draw3 的真实移动画布实现。

OpenCV 只发布可靠的内容位移，真正修改 Viewport 应当由 Draw3 的正确所有者线程执行。

尤其注意：

- OpenCV 结果可能比 Draw3 帧率低。
- 必须避免相同 Sequence 重复应用位移。
- 需要避免 Delta 消息丢失造成永久位移缺失。
- 如果使用 FIFO，保证每次累计位移应用一次；如果采用 Latest-Only，应考虑发布绝对累计位移或相对于已确认基准的目标 Viewport。
- 不得使用过期会话的结果修改新的工作区或画布。
- 文档/工作区切换、窗口销毁、设备失效时应安全停止功能。
- 避免每个特征点或每张截图直接访问 D3D11 DeviceContext。

墨迹应该通过同一 Content/View Transform 跟随，而不是修改已经保存的全部 Stroke 点。

### D. 渲染正确性

重点验证：

- L2 已完成墨迹在视口变化后仍然可见。
- 新露出的区域由已有 Canvas Tile 恢复。
- 退出视图调整后新绘制的笔划坐标正确。
- 橡皮擦作用于移动后的正确内容位置。
- Undo / Redo 不因为移动视口而丢失历史。
- 画布清空、窗口 Resize、显卡资源恢复不能出现旧快照残影。

如果现有移动画布已解决相关问题，直接复用。不要再建立第二套长期存在的 GPU Canvas 状态。

### E. 退出时序

用户再次点击按钮时：

- 停止追踪器采样与结果发布。
- 阻止旧 Session 的异步结果继续提交。
- 保留最后一次可信变换。
- 恢复画布正常输入。
- 确认渲染状态可继续书写。
- 清理本会话截图与 OpenCV 临时资源。

如果当前处于 Paused，也执行同样的退出流程。

## 第六阶段：控制台调试输出

本次必须提供**可实际查看的控制台诊断输出**，为以后调查性能、截图黑帧、定位丢失和漂移提供依据。

优先研究现有：

`Draw3.DiagnosticOutput.cpp/.h`

尽量复用其异步、非阻塞的输出机制，而不是在绘制热路径直接大量执行 `std::cout`。

如果 GUI 程序正常启动时没有控制台，可以设计显式的开发调试开关或命令行参数，使开发者能够打开 Console 或连接已有 Console。

不要每次普通用户启用功能就强制弹出控制台。

建议统一前缀：

`[ScrollFollow]`

### A. 状态日志

必须记录：

- Session ID。
- 开始、结束、初始化成功或失败。
- 捕获初始化、穿透开启和关闭。
- Tracking / Paused 状态变化。
- 停止原因与资源释放结果。

### B. Mag 日志

记录：

- 捕获窗口与 Source Rect。
- 图像分辨率和格式。
- 每次或采样汇总的截图耗时。
- 是否获得有效图像。
- 黑屏检测数据。
- 初始化及运行中的 API 错误码。
- 实际采样 FPS。

### C. OpenCV 日志

记录：

- Frame Sequence。
- 原始特征数、剩余特征数。
- 成功跟踪数和内点数。
- Forward-Backward 误差。
- 位移 dx/dy。
- 累计位移 x/y。
- 置信度。
- 本帧被接受还是拒绝。
- 特征补充数量。
- 进入 Paused 的详细原因。

### D. Draw3 日志

记录：

- 接收到的会话 ID / Sequence。
- 应用的实际位移。
- 变换前后的 Viewport。
- 是否发生坐标钳制。
- 是否触发视口恢复、Tile 恢复或强制重绘。
- 停止后最终 Viewport。

日志示例：

```text
[ScrollFollow][State] session=3 state=Initializing
[ScrollFollow][Mag] frame=1 size=1920x1080 capture_ms=8.2 valid=1
[ScrollFollow][Tracker] frame=12 tracked=184 inliers=160 confidence=0.91 delta=(0,-24.3) total=(0,-356.8)
[ScrollFollow][Relay] frame=20 old=108 added=92 total=200
[ScrollFollow][Viewport] session=3 seq=20 applied=(0,-18.2) viewport=(0,421.6)
[ScrollFollow][Tracker] frame=38 confidence=0.19 accepted=0 reason=insufficient_inliers
[ScrollFollow][State] session=3 state=Paused reason=low_confidence
```

以上是日志格式示例，不是固定参数。

控制台默认不要每帧打印过多信息；可以按时间间隔输出统计信息，并保留详细日志模式。

**错误与状态转换应立即记录；高频性能统计可以每秒汇总。**

诊断输出不能明显降低 OpenCV 跟踪和 Draw3 呈现性能，也不能引入无界日志队列。

## 第七阶段：依赖、构建和兼容

当前项目使用 MSBuild、C++20、vcpkg，支持 Win32/x64/ARM64。

请调查 OpenCV 当前是否已在实际工程中集成。目前主仓库 `vcpkg.json` 没有声明 OpenCV，需要选择符合现有构建体系的最小依赖方案。

初版主要需要：

- OpenCV Core
- Imgproc
- Video（Lucas-Kanade Optical Flow）
- 如需要 RANSAC 仿射估计，则使用 Calib3d

避免无必要地安装 OpenCV 全量模块。

至少尝试：

`InkeysRepo.sln` / `Debug | ARM64`

这里需要按仓库既有编译规则构建整个解决方案，而不是孤立编译某一个 `.cpp` / `.cppm`，以免遗漏 PptCOM 等工程依赖。

同时尽可能检查 x64 构建。

若某个 Windows 旧版本或架构不具备此功能所需能力，则功能应保持不可用或安全失败，而不是导致整个 Inkeys 无法启动。

必须保证原本 Windows 7 SP1 + KB2670838 的主程序兼容目标不被这一可选功能破坏。

## 第八阶段：整体完成标准

最终要求至少通过以下测试。

### 功能测试

- 打开后成功截图、初始化并进入穿透。
- 主栏在穿透期间仍然可操作。
- 缓慢滚动时墨迹正确跟随。
- 向下与向上滚动符号正确。
- 到滚动边界时不产生虚假位移。
- 手指抬起后惯性滚动仍然可被追踪。
- 连续滚动多屏后可以补充新特征并继续跟踪。
- 无位移的静态画面不会被错误判定为失败。
- Mag 黑帧和 OpenCV 低可信度时会暂停，不传播错误坐标。
- Paused 状态可以通过按钮退出并恢复绘制。
- 多次启用/关闭不泄漏资源、不产生失效线程。
- 新笔划、橡皮擦、撤回和重做正常。
- UInk 保存和恢复后的 Viewport 正确。
- 原有定格、窗口穿透、白板和 PPT 功能无回归。

### 诊断测试

需要能够从控制台看到初始化、逐阶段耗时、位移、可信度、特征接力以及失败原因。

建议使用预录制图像序列验证算法，再用真实 Edge/Chrome 和 Word 测试端到端行为。

不能运行真实 GUI 或硬件测试时，必须明确写明尚未验证的部分，不能以静态源码审查替代实际测试。

## 第九阶段：不属于本次任务的后续功能

请保留合理的模块扩展能力，但**不要实现**以下内容：

- 跟踪丢失后的自动重新定位。
- 用户手动选择锚点或手动移动校准。

- 多个独立滚动区域。
- 全局特征地图、回环检测、复杂视觉 SLAM。
- 复杂缩放、旋转、透视变换及网页重排追踪。
- 用户设置页面、可配置跟踪参数。
- 将视觉特征和追踪历史写入 UInk。

当前实现只需要留下清晰的状态和接口，不要预先编写大量尚未使用的框架代码。
