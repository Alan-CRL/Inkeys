2. Codex 写入。
3. Claude 构建、跑自检。编译错误由 Claude 直接修（小）或回交（大）。
4. 审查：
   - Claude 读完整差异：对照设计逐条核对；找设计没写到的边界；确认没有越界改动；编码与换行（UTF-8 BOM、CRLF）。

   - 另起 Codex 只读审阅（不给它实现者的结论）。
5. 修复与复核。
6. 在本文件“实施结果”里记下：调用次数、发现的问题与处置、与设计的偏差、未验证的事项。
7. 在仓库外保存该步差异（`%TEMP%\inkeys-codex\phase-c1\`）。

验证：

- `InkeysRepo.sln` `Debug|ARM64` 构建通过，新模块首次即编译通过。第一次链接报 `LNK1104`（`Inkeys.exe` 无法打开，当时没有进程占用、文件不存在），原样重建成功，原因没有查明。

- 三个新文件均为 UTF-8 BOM、CRLF。

Claude 的改动：

- **规整改为不动点**。按任务说明的顺序（先按代价合并，再按数量上限合并），为数量上限做的合并可能让别的一对变得划算，于是对同一结果再规整一次还会变。Codex 在报告里指出了这一点。改为同一个循环：只要“最小浪费的一对值得合并”或“数量超限”就合并。随机用例增加“再规整一次不变”的断言。`design.md` §4.3 的四条规则含义不变，这是对第 2、3 条执行顺序的补充。
- 按审阅意见补强两条用例（容量溢出时比较整个序列；阈值取整的非整数边界），并在 `Rects()` 上注明规整前可能含相交矩形。

审阅结论与处置：

| 意见 | 处置 |
| --- | --- |
| 负的固定开销被当作 0，与“按规则不合并”不一致 | 不改。任务说明里就是这样规定的，负值没有实际含义 |
| 容量用例在实现忽略第 17 个候选时也能通过 | 已补强 |
| 密度用例没有覆盖阈值的非整数边界 | 已补用例，并用变异验证确认它会失败 |
| `Rects()` 规整前后是同一个接口，使用方忘记规整会让像素被合成两次 | 加注释；第 3 步在渲染器入口加不相交断言（`design.md` §6.1 已有） |
| 后置条件、终止性、整数溢出、模块编译与工程接线 | 审阅未发现问题，与 Claude 的阅读结论一致 |

与设计的偏差：`Area()` 在面积之和超出 `long long` 时返回上限值（Codex 自行加的饱和处理，画布尺寸下不会触发，保留）。

### 第 2 步：E1 圆形橡皮与粗笔（2026-11-23）

Codex（`gpt-6.2-sol`，High，标准档）写入调用 4 次，其中前 3 次按“矛盾即停”没有改代码，各给出一个成立的反例；第 4 次写出实现。只读审阅 1 次（结论见下）。

改动：`Assets/inkVertexShader.hlsl`（尾部分支按横条展开）、`Draw3.RendererPrimitives.cpp`（`DrawStroke` 按批选 K、写常量缓冲的 `padding`、顶点数）、`Draw3.Renderer.cppm`（开关 `SetSweepOnlyStrokeGeometryEnabled`，默认开）、`Draw3.Renderer.cpp`（自检 `RunSweepOnlyStrokeGeometryValidation`，由 `--draw3-renderer-upload-test` 运行）。像素着色器未改。

设计修正共六处，已写入 `design.md` §8.2：

| 来源 | 修正 |
| --- | --- |
| Claude 开工核对 | 起点后方的外圈也要画（改为挖洞）；外沿用 `sqrt((R+2)² − y²)`；横条重叠 1 像素 |
| Codex 第 1 次 | 横条与原四边形求交（原四边形会截断大的端点圆，保持现状）；洞的半径不超过前一段实际画过的范围，每批第一段不挖洞 |
| Codex 第 2 次 | 一端圆包含另一端的线段按原四边形画（截断边穿过饱和区，取整后会差个别像素） |
| Codex 第 3 次 | 一批里有非有限或负的数值时整批 K=1 |

Codex 自行加的保守条件：坐标或半径绝对值超过 65536 的批次 K=1（保留）。

Claude 的改动：

- 前一个点半径小于 1 时不挖洞（那条线段在像素着色器里混入细线覆盖，不保证写满）；补“笔锋收尾”“笔锋起笔”两条用例。
- 自检改用独立的渲染器实例：原写法推进了结构化缓冲游标，使既有断言 `composite Map failure preserves ink state` 失败。
- 去掉“透明或饱和像素逐位相同”的断言：实测有 2–3 个像素在端值边界上差不到 1 级，与抗锯齿带上的差别同源。漏画仍由“最大差值不超过 1/255”把关。

验证（WARP 离屏）：

- `InkeysRepo.sln` `Debug|ARM64` 构建通过，六个着色器均重新生成。
- `--draw3-renderer-upload-test`：`PASS failures=0`。21 组用例 × 擦除、绘制 × 不透明、半透明：最大差值 1/255；有差别的像素都在抗锯齿带上（每例几十到两千个，Retain 上 0.0005–0.0024，Add 上 1 级）；两个截断反例逐像素相同；非法数值批次 K=1、零差别。
- 变异验证：把洞的半径从 `r1 − 2` 改成 `r1 + 1`，36 项断言失败、最大差值 0.988；还原后通过。
- Win7 受保护着色器：`Draw3.Win7GuardedShader.h` 只含一个 `ps_5_0` 程序，顶点着色器由独立资源加载，本步不需要重新生成（Codex 三次独立得出同一结论；Claude 未另行复核头文件字节）。

构建中遇到的两个环境问题：

- `LNK1000`（增量链接内部错误）：重建即过。
- 一次构建日志里出现 `failed writing ...inkVertexShader.cso`，但 MSBuild 退出码为 0，可执行文件嵌入的仍是上一次（变异版）的着色器，自检因此照旧失败。`touch` 源文件后重建恢复。**以后改着色器必须在构建日志里确认对应的 `compilation object save succeeded`，不能只看退出码。**
- 变异那次自检有 36 项失败而进程退出码为 0（此前有失败时为 1），原因未查。判断通过与否以输出里的 `PASS failures=0` 行和 `FAIL` 计数为准。

未验证：

- 硬件显卡上的像素一致性（自检只跑 WARP）。
- 实际耗时：需要用户用大橡皮取一次阶段耗时日志，对比抬笔时的 GPU 几何段最大值。
- WARP、兆芯上每段 12K 个顶点的开销；Win7 实机。
- Win32、x64 配置的构建。

与设计的偏差：每次增量提交的第一段仍画完整（跨调用接续推迟，见 `design.md` §8.3）。

差异备份：`%TEMP%\inkeys-codex\phase-c1\step2.diff`。

#### 第 2 步的实机数据与档位调整（2026-11-23）

#### 第 2 步的硬件基准与档位定稿（2026-11-23 晚）

用户第二份日志（`21-12-41`）没有打开画布调试；第三份（`21-17-32`）用的是小橡皮，与此前不可比。Claude 临时在离屏自检里加了一段硬件显卡基准（环境变量触发、限制分条上限），测完已用备份还原三个文件，工作区里没有残留（已 grep 确认）。数据见 `research/dirty-stats.md` 末节。

定稿后重新构建（删除 `Inkeys.ilk` 后链接成功，确认可执行文件时间为最新），`--draw3-renderer-upload-test` 输出 `PASS failures=0`，96 项，最大差值 1/255；`--draw3-dirty-region-only` 失败数 0。

本步又遇到两次 `LNK1000`：链接失败时旧的可执行文件留在原处，随后的自检跑的是旧文件。**以后每次构建后先看退出码，再确认可执行文件的时间，然后才跑自检。**

| 子步 | 内容 | 验证 |
| --- | --- | --- |

比设计更保守的一条规则（Claude 加）：本帧有平移（可信快照合成）、清空碎裂、激光轨迹、激光笔尖、点击光波或粒子时，区域折叠为单个矩形（`frameNeedsSingleRect`）。这些路径各自只消费一个矩形，其中激光笔画层的绘制带覆盖率纹理的内部状态。留给第 6 步。

Claude 的改动：

- 删掉 Codex 在 3b 加的一段兼容分支。它复刻了旧代码的一个瑕疵：没变的激光笔尖与脏区部分重叠时，旧代码不把笔尖整个并入却整个重画。新闭包把整个笔尖并入再重画。起因是任务说明里“合成范围不得变大”写得过严。这是一处有意的行为变化。
- 还原 Codex 在 3c 对平移帧的改动（快照合成失败时改走普通合成）。不在范围内，平移期间 L2 可能正在恢复瓦片。
- 呈现后的观察回调改回在调用处计算外接矩形，不从呈现端的观测结构取（提前返回的路径上那里可能是上一帧的值）。
- 修复审阅的 P1（见下）。

审阅结论与处置（无 P0）：

| 意见 | 处置 |
| --- | --- |

### 第 6 步：激光与粒子来源细化（2026-11-24）

Codex：只读开工核对 1 次、写入 1 次、只读审阅 1 次。`design.md` §11 原定“取数后定粒度”；用户要求先把 C1 做完，这一步按保守粒度实现，没有先取数。

开工核对的结论：帧区域被折叠成单矩形的四个激光条件里，真正需要单矩形的只有“未烘干的激光层”（`DrawLaserStrokeLayers` 每次调用都要清并重画覆盖，按矩形调用会成倍增加栅格化）。已烘干轨迹的合成是一次带裁剪的贴图绘制，按不相交矩形分别调用结果相同。笔尖、点击光波、粒子是不裁剪的整体绘制，只要它们各自的范围在帧区域内就正确，与区域有几个矩形无关。

实现（只改 `Draw3.DrawingController.cpp`）：

- 已烘干轨迹的合成改为对帧区域的每个矩形各调用一次 `ResolveLaserCompositedColor`。
- 折叠条件收窄为：平移快照、清空碎裂、存在可合成的未烘干激光层、点击光波可见。“激光生命周期非空”“笔尖可见”“粒子在画”不再折叠。
- 淡出、溶解、聚拢的每帧脏区由整组轨迹的外接矩形改为每条已烘干笔画各一个矩形；仅当这些矩形的外接恰好等于 `laserStableBounds` 时才这样做，否则沿用原范围。轨迹到期那一帧仍用整组范围。
- 没有做：按点列把长笔画分段、粒子按批次给矩形。前者要等数据，后者批次多且分布广，收益有限。

审阅：无 P0。P1 即上面的光波范围，已补。P2：新增用例没有覆盖“逐笔矩形是否漏掉某条笔画”这一层的产品逻辑（它在帧循环里，无窗口用例够不到），未补。
