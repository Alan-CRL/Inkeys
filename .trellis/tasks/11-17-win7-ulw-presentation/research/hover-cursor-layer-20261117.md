# 悬停帧与光标层性能调查（2026-11-17）

> 背景：阶段 A 实机日志发现悬停帧不限速；用户反馈大橡皮、多指橡皮（即使橡皮不大）书写时卡顿，怀疑光标层拖慢了包括墨迹在内的整体体验。本文件只做调查记录，**未改代码**。
> 代码基准 `refactoring/draw@0c8a7337`。简称 C=`Draw3.DrawingController.cpp`、RP=`Draw3.RendererPrimitives.cpp`、EC=`Draw3.EraserCursor.h`。
> 相关既有结论：中期总任务 `research/第5步 Inkeys3_Draw3_4K_Eraser_Pan_Performance_Investigation_20261116.md` §4.4（大游标扩大 dirty）、§5（像素成本）、第348行待办“优化大游标合成范围”。

## 1. 悬停帧不限速

### 1.1 链路（事实）

1. 鼠标移动、笔悬停、工具/外观设置变化都会调用 `RequestDrawingCursorRender()`（`Draw3.WindowControl.cpp` 1165–1374 多处；C:15153、15192），置位一个原子标志。
2. 帧循环每轮 `ConsumeDrawingCursorRenderRequest()`（C:21520）取走标志；标志为真时不进入空闲等待（C:22088 条件含 `!drawingCursorRequested`）。
3. 本帧脏区 = 上一帧全部光标的包围盒 ∪ 本帧全部光标的包围盒（C:23192–23202，`cursorVisualBounds` 把所有光标并成一个矩形，C:19129–19136）。在这块区域重做“复制 L2 → 合成 L1/L0 → 底纹/调试板 → 画光标”，然后 `Present`。
4. 帧尾节奏只在三种情况等待：有物理接触（C:23535）、漫游/动画（C:23558）、有活动笔画的 deadline（C:23573）。**只有光标变化时三者都不命中**，立即进入下一轮。
5. 鼠标/笔光标样本是“只保留最新值”的信箱（`ReadMouseCursorSample` / `ReadPenCursorSample`），本来就支持合并。

结果：悬停时帧率 = 输入事件率。1000 Hz 鼠标约每秒 1000 帧（阶段 A 日志 `acquired` 600–960/s 与此吻合）；笔悬停按笔的报点率（常见 133–266 Hz），当预设帧率更低时同样超出。

### 1.2 代价

| 后端 | 每个悬停事件的成本 |
| --- | --- |
| DComp | 一次局部合成 + `Present1`。超出刷新率的帧会被 DWM 丢弃（看不到），但 GPU 合成与 DWM 处理照样发生 |
| ULW（Win7 / 回退） | 一次局部合成 + **同步** `Map` 读回 + 行拷贝 + `UpdateLayeredWindowIndirect`，每次都在绘制线程上串行执行 |

光标越大，每帧合成面积越大：橡皮悬停时，光标的旧位置 + 新位置可能达到数十万像素，乘以每秒约 1000 次。

### 1.3 是否需要优化：建议优化（小改动）

- 做法：只有光标变化的帧也按预设帧率走 `WaitForFrameDeadline`（或等价节奏）。信箱只保留最新样本，所以限速只是把多个事件合并成一帧，不会丢掉最终位置。
- 收益：悬停时的 GPU/DWM 负载降到原来的 1/8 左右（1000 → 120 帧/秒）；ULW 下影响最大，也是阶段 B 测量基线的前提。
- 代价：应用绘制的光标最多晚一个预设帧间隔（120 预设约 8 ms，240 预设约 4 ms）。目前超出刷新率的帧本来就看不到，实际观感差异应该很小。系统箭头光标不受影响。
- 风险点：限速等待期间如果落笔，必须立刻唤醒，不能推迟落笔首帧。已核对：`ContactInputCoordinator::WaitForFrameDeadline`（`Draw3.ContactInput.cpp:1325`）在 `frameWakeGeneration` 变化时提前返回，并且会补看工作阶段已到达的 Down/Up；Move 不唤醒（悬停本来就不需要）。复用它即可满足要求，实现时仍需用测试确认。

### 1.4 补充：鼠标按下书写时同样突破预设帧率（用户追问，已读码确认）

- 链路：`WM_MOUSEMOVE` → `PublishMouseCursorSample`（`Draw3.WindowControl.cpp:1836`）→ 位置变化即 `RequestDrawingCursorRender()`（1901，**不区分是否按下**，只排除移动模式）→ `RequestControlWake()` → `PublishControlWake()` → `SignalWake()`（`Draw3.ContactInput.cpp:381`、468，默认 `interruptFrame=true`，递增 `frameWakeGeneration`）→ 正在执行的 `WaitForFrameDeadline` 立即返回（`Draw3.ContactInput.cpp:1325` 起）。
- 结论：鼠标按下书写时，每个移动消息都会打断帧尾等待，实际帧率约等于鼠标报点率（受单帧工作耗时限制）。例如预设 30 FPS、1000 Hz 鼠标时会远超 30 FPS。
- 对照：笔接触期间有意不逐包唤醒（1797–1801 注释“接触期间由活动绘制帧读取 mailbox，避免每个 Pen 包额外唤醒”，只在状态变化或悬停时请求）；触摸与笔的 Move 走 `PublishMove`，本身不唤醒。**只有鼠标路径缺少这个区分**。
- waitable 不是帧率上限：SyncInterval 0 下令牌约 1 ms 回补，既不限速也谈不上被“越过”；被绕过的是预设帧率的帧尾等待。
- 鼠标按下不动：信箱 `Publish` 在位置、接触、来源都相同时返回未变化（`Draw3.PenCursor.cpp:248–257`），不会请求重绘、也不唤醒，即使系统补发同坐标的移动消息也一样。帧循环仍按预设帧率空转（存在物理接触，C:23535 分支），用来检查输入、推进停笔收敛；笔锋收敛冻结（`idleFrozen`，SG:2210）后 `frameDirty` 为空，不合成、不 Present（C:23261 附近 `!IsEmptyRect(frameDirty)`），也不等待 waitable（令牌未消耗）。例外：速度橡皮回缩动画期间仍按预设帧率呈现，直到动画结束；静止的橡皮接触走 `WaitForEraserIdle`，不空转。
- 修复方向（未实施）：鼠标按下期间与笔一致，位置变化只更新信箱、不打断帧节拍（只在有效性/接触状态变化时唤醒）；与 §1.3 的悬停限速可以合并为同一个小改动。

### 1.5 鼠标光标改动方案（讨论稿，未实施）

**现状对照（已读码）**

| 场景 | 笔光标 | 鼠标光标 |
| --- | --- | --- |
| 数据来源 | RTS `InAirPackets`（悬停，RTS:1471）/ `Packets`（接触，RTS:1526）→ `PublishPenCursorSampleImpl` | `WM_MOUSEMOVE` → `PublishMouseCursorSample`；鼠标书写本身是 RTS 的 `TDK_Mouse` 接触，移动走 `PublishMove`（不唤醒） |
| 悬停 | 位置变化即请求重绘并打断帧等待（`Draw3.WindowControl.cpp:1801`）→ 帧率 = 笔报点率 | 同左 → 帧率 = 鼠标报点率 |
| 接触中 | **不逐包请求**，只在 valid / inContact / inverted 变化时请求；活动帧按预设帧率读信箱 | **逐个移动都请求并打断帧等待** → 突破预设帧率 |
| 接触中不动 | 无请求 | 信箱去重，无请求 |

**方案 A（推荐先做，一行级改动）：接触中与笔对齐**

- `PublishMouseCursorSample` 的请求条件从 `!CanvasPanMode() || stateChanged` 改为与笔相同的 `stateChanged || (!sample.inContact && !CanvasPanMode())`。
- 效果：按下书写时光标由活动帧（按预设帧率）读取信箱最新位置；按下/抬起仍立即唤醒；悬停行为不变。
- 依赖的前提：按下期间存在活动的物理接触帧。鼠标按下若被拒收、没有形成活动笔画（准入拒绝、兼容消息抑制等），绘制的光标在拖动期间不会跟随，直到抬起或下一次状态变化。笔路径目前也是同样的前提。
- 备选（如果实测发现上述边界问题）：接触中仍置位重绘标志，但改用**不打断帧等待的唤醒**（只唤醒空闲等待，不递增 `frameWakeGeneration`；内部已有 `SignalWake(interruptFrame=false)` 机制，需要新增对外接口）。有活动帧时不影响节拍，没有活动帧时也能刷新光标。

**方案 B（可选，悬停）：悬停帧率上限**

- 用户倾向：不绘制时按事件唤醒可以接受。
- 顾虑：超过刷新率的悬停帧看不到；大橡皮光标悬停时每帧要合成很大一块区域；ULW 下每帧还要做同步读回和 ULW。
- 若做：悬停帧上限取**显示刷新率**而不是预设帧率（避免 30 预设时悬停光标只有 30 Hz）。前提是悬停请求也改为不打断帧等待的唤醒，否则下一个悬停事件会立刻打断限速等待；落笔（Down）仍通过 `frameWakeGeneration` 立即唤醒。笔悬停和鼠标悬停一起处理。
- 建议先做 A，B 等大橡皮悬停与 ULW 的实测结果再定。

**验证要点**：预设 30 FPS 鼠标快速书写，画布调试帧率应接近 30；鼠标按下/抬起首帧延迟不变；鼠标书写时光标与笔迹同步；移动模式、选择模式、鼠标速度橡皮（回缩动画）、激光笔（鼠标）行为不变；相关无窗口测试（光标/鼠标唤醒类）需复跑。

### 1.6 补充：RTS 拓展模式同样受影响（用户追问，已读码确认）

- 鼠标的笔迹输入与光标是两条独立的路：
  - 笔迹：RTS 模式（含拓展）下来自 RTS 的 `TDK_Mouse` 接触（`Draw3.RealtimeStylus.cpp:989`），移动走 `PublishMove`，不唤醒；兼容模式下来自窗口消息 `HandleCompatibilityMouse`（`Draw3.WindowControl.cpp:993`）→ `MouseInputState::Move` → `PublishMove`（`Draw3.MouseInput.h:98`），同样不唤醒。
  - 光标：两种模式下窗口都照常收到 `WM_MOUSEMOVE`（RTS 不吞鼠标消息）。RTS 模式由主消息分支处理（`Draw3.WindowControl.cpp:2825` 起，过滤触摸/笔的提升消息后在 3005 发布，`inContact = 按键按下`）；兼容模式由 `HandleCompatibilityMouse` 在 1036 发布（`inContact = mouseInput_.Active()`）。
- 两条处理分支最终都汇合到 `PublishMouseCursorSample`，这是鼠标打断帧节拍的唯一来源。因此 RTS 拓展模式**同样有这个问题**；阶段 A 日志（RTS Extended）里悬停时约 900 次/秒的 Present 也印证了光标路径在工作。
- 方案 A 只改 `PublishMouseCursorSample` 一处即可同时覆盖两种模式。触摸、笔接触不经过这条路径，不受影响。

## 2. 光标层是否拖慢墨迹（多指 / 大橡皮）

### 2.1 事实

1. **光标绘制本身很便宜**：每个光标是一个带纹理的 quad（RP `DrawTransientDrawingCursor`），橡皮图案是缓存的精灵纹理（RP:264 `EnsureEraserCursorSprite`）。
2. **精灵缓存按样式各一份**，烘焙尺寸为 2 的幂档位（32…1024），**只升不降**（EC `ResolveEraserCursorBakeShortSide` 继承 previous 档位）。多个尺寸不同的手指共用同一份，不会来回重建。但每次尺寸首次跨过更高档位时，会在**绘制线程上同步 CPU 栅格化整张精灵和完整 mip 链**（最大 1024×1024），并 `CreateTexture2D`。这是一次性的卡顿来源，耗时未测。
3. **所有光标与本帧全部变化共用一个包围矩形**（C:23192–23202）。只要任一光标与上一帧不同（`cursorVisualsEquivalent` 逐个比较，C:19118–19126），就把**全部**光标的旧、新位置都并进 `frameDirty`。
4. 多指橡皮在接触期间每帧都在动，因此每帧的 `frameDirty` 至少是“所有手指光标 + 所有橡皮落点”的外接矩形。两根手指分在屏幕对角时，外接矩形接近全屏。
5. 墨迹、橡皮、光标在**同一帧、同一线程、同一次合成和 Present** 里完成。光标导致的大面积合成会直接拉长这一帧，墨迹延迟随之上升。

### 2.2 推断

- 多指（哪怕橡皮不大）卡顿：手指之间的距离决定外接矩形大小，与橡皮尺寸关系不大。手指分得越开，越接近每帧全屏合成。2880×1920 约 550 万像素，合成要读写 L2、L1/L0 的 Add/Retain、底纹等多张纹理，粗估每像素 30–40 字节，即每帧约 200 MB，120 帧/秒时约 24 GB/s（未实测，只是数量级）。DComp 下 `Present1` 的脏矩形也随之变大，DWM 要重新合成同样的面积。
- 大橡皮单指卡顿：橡皮本身的栅格化成本（L1 写入面积大、重叠落点重复覆盖）+ 光标旧新位置的并集 + 第5步文档指出的“纯橡皮帧仍整层清 L0、合成仍采样恒等层”叠加。
- 光标在这里是“放大器”：它本身便宜，但会把墨迹真正变化的区域扩大成大块重合成。
- 首次放大橡皮（尺寸跨档）时的一次性卡顿，可能来自精灵同步栅格化。

### 2.4 可选优化方向（供讨论，未实施；与第5步“4K 橡皮与漫游性能”重叠）

1. **悬停限速**（§1.3），小改动。
2. **多矩形脏区**：维护少量互不相交的脏矩形（例如最多 4–8 个，过多时再合并），按矩形分别合成。DComp 的 `Present1` 原生支持多个 dirty rect；ULW 只有一个 `prcDirty`，提交时仍用外接矩形，但 GPU 合成与读回可以只做各个小块。中等改动，涉及合成与呈现路径。
3. **光标与墨迹分层**：光标画在独立的 DComp visual/表面上，光标移动不再触发墨迹重合成。改动大，与“Drawpad3 统一窗口/控件同窗渲染”的方向需一起设计。
4. **精灵预热/异步烘焙**：启动或切换外观时预生成常用档位，避免首次跨档在绘制线程同步栅格化。
5. 第5步文档已列：纯橡皮帧跳过 L0 整层清除、合成跳过恒等层采样。

## 3. 后续测试计划（用户提出，待安排）

- **高负载下的帧率与延迟**：需要一个可调强度的 CPU/GPU 加压脚本（CPU：N 个忙线程；GPU：独立进程跑可调负载的全屏着色器），在 60/120 Hz、各预设帧率、waitable 等待开/关下对比书写延迟与卡顿。
- **熔断路径**：按设计，GPU 再慢也只会让自适应超时变长（上限 200 ms），等待照常成功，**单纯加压基本不会触发熔断**（熔断条件是连续 ≥8 次超时且持续 ≥1 s，即句柄丢信号）。要测熔断后的重建与回退，需要一个故障注入开关（例如环境变量让等待强制超时或失败），这需要改代码，留待后续实现。
- 加压脚本放在仓库外或 `Scripts/` 下需由用户决定；本轮不写代码。
