# 阶段 C1.5：白板翻页与 UInk 加载提速

> **2026-11-25 起与 C1.4 联合实施**：需求、设计与验收以 `../11-24-uink-1-1-adaptation/`（`prd.md`、`design.md`、`implement.md`）为准。本任务的计时插桩与基线数据并入联合任务使用；冷页加载的 CPU 与 IO 部分在联合任务中完成，**GPU 冷重建移交 C2**。下文保留为历史记录。

## 背景

用户反馈白板翻页、恢复 UInk 墨迹很慢。2026-11-24 两次只读调查的结论（行号以调查时为准，实施前复核）：

- 翻页后目标页基本都是冷页：离开的页保存完成后被驱逐，翻页时丢弃热前像与合成缓存（`Draw3.DrawingController.cpp:23598`）。**用户确认这符合设计**：平时要释放缓冲，翻页后从磁盘读回是预期行为，本任务不改变这一点。
- 冷页加载路径上的开销（按代码推断的可能性排序，均未实测）：
  1. 绘制线程上用 JsonCpp 解析一份与 UInk 正文重复的整页历史，逐笔计算足迹；有撤回日志（journal）时整页撤回到底再重做一遍做校验（`:1027`）；离开的页在绘制线程上同步序列化为 JSON（`:17682`）。
  2. GPU 冷重建逐笔、逐块：每笔在每块 256 合成瓦片上约 2 次清除、3 次绘制、3–4 次上传；跨多块的长笔在每块里重复上传；全部可见瓦片在一帧内同步完成。
  3. 读盘时对整个多页文件做 SHA-256；保存时复制整个文件再校验；Store 只有一个后台线程，快速翻页时加载可能排在保存之后。
- 脏区不是问题：翻页只设一次整屏脏区。
- 读盘、解析、GPU 恢复各段目前都没有耗时日志。

## 需求

1. **先测量**：给冷页加载补上分段计时输出，至少覆盖：保存离开页（序列化）、读盘与校验、解码、历史恢复（JSON 解析、逐笔恢复、足迹、journal 校验）、GPU 恢复（瓦片数、笔画数、绘制次数）、从翻页命令到首次呈现的总时长。输出按页一行汇总，不逐笔刷屏。用户用较重的页面实测后，按数据决定后续优化顺序。
2. **按数据优化**，候选方向（以实测为准，不预先全部实施）：
   - 历史恢复移出绘制线程，或去掉与 UInk 正文重复的 JSON 副本。
   - journal 校验降低成本（例如只在必要时做，或换成不需要整页往返的校验）。
   - 读盘校验不再每次对整个多页文件做 SHA-256。
   - 离开页的序列化移出绘制线程。
   - GPU 冷重建减少逐笔、逐块的重复上传与合成。
3. 翻页后整页为冷、从磁盘读回的设计保持不变；加载 CPU 数据仍是整页，GPU 只按视口恢复。
4. 与 C2 的边界：瓦片直接显示、平移与缩放显示、缓存跟随画布都属于 C2。本任务只做加载链路本身；GPU 冷重建若与 C2 的显示改造重叠，留给 C2。
5. **PPT 的 UInk 读取同样纳入本任务**（2026-11-24 用户决定）：先补与白板同口径的计时并实测，再按数据优化。
6. **为统一封装做准备**（2026-11-24 用户决定）：桌面画布、PPT、白板的翻页本质相同；桌面画布与 PPT 未来也可能支持拖动和缩放，与白板同一套逻辑。本任务改动的加载、保存、安装链路要按“与工作区无关的页面存取与安装”来组织，避免再写一套白板专用实现；真正把三处统一成一个模块留到 C3。

## 实测结论（2026-11-24 第一次，Debug 构建）

详见 `research/load-timing-logs.md`。冷页加载 290–370 ms，按占比：GPU 冷重建命令提交 40–45%，重复的历史 JSON 解析 25–30%，整文件 SHA-256 读盘约 15%，足迹约 10%；journal 校验只有约 3 ms。保存链路：离页序列化 36–52 ms 压在翻页上，后台整文件重写 120–150 ms 会推迟紧接着的冷加载。

## 验收

- [ ] 冷页加载各段都有计时输出，用户实测给出优化前的基线数据。
- [ ] 按数据实施的优化在同一页面上有可比的前后数据，总时长明显下降。
- [ ] 翻页、撤回重做、journal 恢复、保存与驱逐的行为与原来一致（含损坏 journal 不部分替换已打开页面的约束）。
- [ ] 相关自检与无窗口测试通过；未覆盖的路径如实说明并实机验证。
