## 口径

- **来源矩形**：每次并入 `frameDirty` 的非空矩形。
- **区域**：把来源矩形裁剪到画布后，相交的合并成外接矩形，直到两两不相交。这与首版拟用的“相交即合并”规则一致，所以“区域面积之和”就是首版多区域方案能达到的合成面积。它没有按代价再合并相距很近的区域，实际方案的区域数会更少、面积略大。
- **外接矩形**：全部来源矩形的并集外接矩形，即现在实际合成与呈现的范围。
- 调试板与调试标记自身并入的范围不计入。
- 强制整屏的帧（平移、翻页等）单独计数，不计入面积平均。
- 通过引用把 `frameDirty` 传给被调函数的几处（形状 UI、画布命令、激光烘干、图形构造预览等）无法逐个登记，按扩大后的外接矩形保守计入一个来源，并计入 `untracked`。保守的意思是只会低估多区域的收益。
- 已知偏差：画布调试打开时，调试板刷新会让“只要有脏区就并入当前光标”这条规则多触发几次。

## 日志字段

每秒一行，Debug 级别，前缀 `[Draw3Diag][dirty-stats]`：

| 字段 | 含义 |
| --- | --- |
| `frames` | 有脏区且未强制整屏的帧数 |
| `full` | 强制整屏的帧数 |
| `multi` | 区域数不少于 2 的帧数 |
| `rawAvg` | 平均每帧来源矩形数 |
| `regionsAvg` / `regionsMax` | 每帧区域数的平均与最大 |
| `boundsPct` | 外接矩形面积占画布的平均百分比（现状） |
| `regionPct` | 区域面积之和占画布的平均百分比（多区域后） |
| `multiBoundsPct` / `multiRegionPct` | 同上两项，只统计多区域帧 |
| `untracked` | 保守计入的次数 |
| `overflow` | 单帧来源超过 64 个的次数 |

## 取数方法

1. 日志级别调到 Debug，打开画布调试。
2. 依次做下列场景，每个持续 5 秒以上，记下各自的时间段：
   - 单指书写；两指靠近书写；两指分在屏幕对角书写。
   - 单指大橡皮；两指大橡皮靠近；两指大橡皮分在对角。
   - 大橡皮只悬停移动。
   - 激光笔画几条相距较远的线后等待留存与淡出；开启粒子时重复一次。
   - 一条对角长线的荧光笔。
   - 撤回、重做一条长对角线。
3. 取日志中对应时间段的 `dirty-stats` 行。

### 读数

1. **两指对角书写是最大的浪费**：现在每帧合成 22–78% 的画布，实际变化不到 0.15%，相差两到三个数量级。两指靠近时也有约 6 倍，但绝对值很小。
2. **两指大橡皮对角显示为 1 个区域，是统计口径的限制，不是没有收益**：所有光标的范围先被 `cursorVisualBounds` 并成一个矩形，再并入帧脏区（`Draw3.DrawingController.cpp` 的 `cursorVisualBounds`，逐个 `UnionRectInPlace` 后返回一个 RECT）。这个矩形横跨两指，把所有来源都连成了一块。现状 40–64% 是真实的；改成逐个光标给矩形后才能看出多区域的面积，预计接近单指的两倍（约 11–13%）。
3. **单指大橡皮每帧约 6% 画布（约 30 万像素）**，基本就是光标与橡皮本身的大小，多区域对它没有帮助。
4. **激光留存淡出每帧 67–75%，加粒子后 31–100%**，持续整段留存时间，区域数都是 1。要缩小只能让来源给更细的矩形（按笔、按分段）。
5. **撤回、重做一条对角长线是一帧 48–77%**。分段矩形能大幅缩小。
6. **清空碎裂每次约 3 秒、每帧 86–100%、约 115 帧每秒**。碎裂范围是被清墨迹的外接矩形，属于效果本身的开销，多区域帮不上。
7. **悬停每秒 650–800 个脏帧**，同时段等待对象每秒被获取 691–811 次，即每秒合成并提交 700–800 次，显示器是 120 Hz。悬停不限速是 2026-11-17 的既定决策（`11-17-cursor-frame-pacing`：悬停保持按事件唤醒）。每帧只有 0.16% 画布，单帧很轻，但次数是刷新率的 6 倍。
8. 书写与擦除时每秒脏帧 60–96，低于 120。脏帧由输入驱动，这个数不能直接当作掉帧的证据。

### 对未定项的含义

- **容量**：实际区域数最多 3。光标改为逐个给矩形、激光与长线分段后会变多，首版 16 个足够，是否能更小等分段方案定了再看。
- **代价参数**：两指对角的差距是数量级的，合并阈值取得粗一点也不影响这类场景；阈值主要影响“两指靠近”这类区域相邻的情况，那里绝对值本来就小。所以首版可以用保守的固定阈值，不必先做精细标定。
- **分段粒度**：激光淡出、撤回重做、粒子是区域数为 1 而面积很大的三类，分段的收益主要在这里。

对实现顺序的含义：E1（只画新扫过的部分）优先级最高，它同时压低第 2、3、4 条；其次查清第 4 条的原因；精灵烘焙值得纳入。多区域合成在这台机器上收益小，主要价值在核显、WARP 和 ULW。

   - 起笔时 L1 不是空的（里面有别的内容）。
   - 两次提交之间，上一批的末点被改过（位置或半径）。
   - 建模器尚未给点时的落点兜底，或某次绘制失败。
   8 笔里 2 笔出现，其余正常，更像是与起笔时序有关的第一种，但这是推断。
3. **抬笔帧会让呈现等待超时**：19:21:43 与 19:21:48 的 `latency` 行各有一次 `gpuBusyTimeouts=1`，等待最长 24 毫秒。
4. 这次橡皮较小，整笔重画是 28–44 毫秒；上次大橡皮是 76–214 毫秒。再次印证成本取决于每段的像素量。

对设计的含义：E1（只画新扫过的部分）把整笔重画本身变便宜，两个来源都受益。在此之上，第一种候选可以单独消除（例如橡皮的落点印记不影响前缀是否可沿用，需要论证与整笔重放的像素一致性）。E3（不计入不出墨的接触）在这份日志里没有出现对应情况（`observers` 始终为 0）。

另记一处与本任务无关的现象：启动时等待对象按 16.67 毫秒刷新周期初始化（`refreshMs=16.6666`），之后 DComp 对齐报告的周期是 8.33 毫秒，而 `latency` 行里的 `refreshMs` 一直是 16.67。是否影响等待超时的计算没有核实。

## 前缀不精确的原因（2026-11-23 深夜，用户要求先查）

### 读码已能确定的一个来源

`NoteL1PrefixDrawn`（`Draw3.StrokeGeometry.cpp`）在一笔起笔或整段重画时把“前缀精确”设为“此刻 L1 是否为空”。L1 是所有接触共用的，所以：

- 多指时只有**第一个落下的接触**起笔时 L1 为空；之后落下的接触起笔时 L1 里已经有别人的前缀，从一开始就不精确。
- 任一接触抬起触发共享层重建时，`RebuildActiveLayers` 先清 L1，再依次重画各接触的前缀；同样只有第一个被重画的接触算精确。

后果：多指擦除后剩下的最后一指，除非它恰好是“第一个”，否则抬起时也走整笔重画。19:21:43 那一笔（两指、前缀不精确）符合这一条。

这一条解释不了 19:21:30 的单指（当时只有一个接触）。

### 新增日志

改动只在 `Draw3.StrokeGeometry.cpp`：前缀从精确变为不精确、或起笔时就不精确时，输出一行 Debug 日志 `[Draw3Diag][l1-prefix] inexact reason=…`。每笔至多几行。这条日志在几何模块里，拿不到画布调试开关，所以只受日志级别控制。

| `reason` | 含义 |
| --- | --- |
| `layer-not-empty` | 起笔或整段重画时 L1 里已有内容 |
| `single-point-mark` | 这一批只有一个点，画的是落点印记 |
| `junction-changed` | 追加时，上一批的末点与这一批的首点不一致（位置或半径被改过） |
| `layer-epoch-changed` | 两次追加之间 L1 被清过或被别的内容写过 |
| `start-point-fallback` | 建模器还没给点，用落点兜底 |

同行还有 `restart`（是否起笔或整段重画）、`batch`（这一批点数）、`prefixCount`、`realPoints`。绘制失败的分支没有加日志（失败本身另有记录）。

验证：`InkeysRepo.sln` `Debug | ARM64` 构建通过，`--canvas-debug-only` 失败数 0。没有启动应用。未提交。

取数：单指大橡皮反复“落下、擦两三秒、抬起”十次左右，看 `lift-path` 出现时它前面最近的 `l1-prefix` 行。

### 前缀原因数据（2026-11-23，日志 `2026-11-23T19-30-04.log`）

这次只有 4 笔（其中橡皮 2 笔），不是建议的十次，但已经抓到了单指的那种情况：

| 时间 | 事件 |
| --- | --- |
| 19:30:17.3 前后 | 第 1 笔橡皮抬起，走尾段路径（GPU 几何段最大 2.0 ms） |
| 19:30:17.449 | `l1-prefix inexact reason=single-point-mark restart=1 batch=1 prefixCount=0 realPoints=1`：第 2 笔起笔，第一批只有一个真实点 |
| 19:30:21.000 | 第 2 笔抬起：`lift-path path=isolated contacts=1 prefixExact=0 points=1428`，整笔重画，GPU 几何段最大 26.2 ms，同秒一次呈现等待超时（25.1 ms） |

**结论：单指走整笔重画的原因是“落点印记”。** 起笔第一帧只拿到一个真实点时，画进 L1 的是单点印记（向右延伸的短胶囊），整笔重放不会画它，于是这一笔的前缀从第一帧起就被标为不精确，直到抬笔。是否发生取决于起笔那一帧建模器给了几个点，所以时有时无（本次 2 笔橡皮中 1 笔，上一份日志 4 次单指抬笔中 1 次）。

到这里整笔重画的来源已经清楚，共三个：

1. 抬笔时还有别的接触（接触数不为 1）。
2. 多指时不是第一个落下的接触（起笔或重画时 L1 非空）。
3. 起笔第一帧只有一个点（落点印记）。

本次日志的其他读数：

- **合成段与面积成正比**：清空碎裂期间每帧 86% 画布，GPU 合成段平均 2.0–2.2 ms、最大 8.6 ms；单指橡皮每帧 3–5% 画布时是 0.16–0.2 ms。本机整屏合成约 2.5 ms，占 120 Hz 一帧预算的三成。核显上会按带宽比例放大。
- **19:30:22–24 每秒 25–38 次整屏清、40–68 次局部清**，约每帧一次，脏区在 4.8–5.8% 画布，接近局部清与整屏清的分界线（1/16 即 6.25%）。看起来是某个每帧重画 L0 的工具在分界线两侧来回切换。没有核实是哪个工具，记在这里供设计时考虑分界线附近的行为。

### 崩溃与卡死的原因：系统虚拟内存耗尽

- 第一份日志 23:20:36，8 个荧光笔接触、其中 4 个同时抬起时，绘制线程抛出 `bad allocation`，绘制循环停止，Host 按设计受控退出。此前一秒 CPU 几何段最大 1005 毫秒。
- 第二份日志 23:21:46，多指笔抬起并重建（约 1300 点）后，UI3 的 Bar 在 23:21:47 报 `0x8007000E`（内存不足）与 `0x8899000C`（需要重建目标），之后每秒重试都失败，界面不再刷新。
- Windows 系统事件日志在 **23:17:25 与 23:19:51 各记录一次“虚拟内存不足”**（Resource-Exhaustion-Detector，事件 2004），列出的占用最多的程序是 ShareX、explorer、vcpkgsrv、node，没有 Inkeys。
- 事后查看（Inkeys 未运行）：系统已提交内存 42.4 GB，上限 47.6 GB；空闲物理内存 0.5 GB（共 15.6 GB）。

结论：两次故障都是系统提交内存耗尽时，应用在多指抬笔这种集中分配的时刻申请失败。没有证据表明阶段 C1 的改动增加了内存占用；本步新增的数据结构都是固定大小或几个元素的小数组。**没有测过应用在多指抬笔时的实际内存峰值**，所以不能排除它在内存紧张时比以前更容易触发，只能说系统层面的原因是确定的。
