## 0. 结论摘要

1. **阶段 A 本身运行正常**：两次会话都检测到正确的刷新率（8.33 ms / 16.67 ms）、没有熔断、没有错误，超时很少。等待耗时平均 < 0.25 ms，最长 28 ms。**没有证据表明 A 造成了长时间卡顿。**
2. **但 A 的等待在当前配置下几乎不起作用**：`Present1` 用的是 SyncInterval 0，DWM 会丢弃被新帧取代的帧并立即回补句柄，所以句柄约每 1 ms 就发一次信号（`signalIntervalMs ≈ 1`）。等待只在 GPU/DWM 真正积压时才会挡住（这正是设计目标“GPU 吃紧时”），不会把帧率压到刷新率。因此“高帧率预设 + 低刷新率屏”时 A 并不改变帧节奏，这个默认策略问题仍未解决。
3. **新发现：悬停帧不限速**。只有光标变化的帧没有帧率上限，鼠标每移动一次就 Present 一次，日志里约 600–960 次/秒。这是 A 之前就有的问题。
4. **预测尖刺**：机制已基本确定，是 A 之前就有的问题，详见 §3。A 会改变采样时机，因此可能影响发生率，但不是根因。
5. **卡顿**：现有日志只能排除 A 的等待是长卡顿来源，并给出几个可疑时间点；无法定位到具体代码，需要补阶段耗时诊断（§4）。

## 2. 阶段 A 指标解读

### 2.1 `acquired` ≈ 900/s 的含义

- 状态机只有在**成功调用 `Present1`** 之后才释放令牌（`Draw3.FrameLatencyGate.h` `OnPresentCalled`），所以 `acquired` ≈ 每秒成功 `Present1` 的次数，不是显示帧率。
- `PresentSwapChain` 调用 `Present1(0, 0, …)`（P:1308）。在 flip 模型下，SyncInterval 0 的帧会被下一帧取代并丢弃，句柄随即回补，所以 `signalIntervalMs ≈ 1 ms`、`waitAvgMs` 仅为 0.001–0.2 ms。
- 每秒约 900 次 Present 的来源是悬停帧（§5）：光标请求帧在帧尾不走 `WaitForFrameDeadline`（C:23525–23605 的分支都不命中），帧率等于输入事件率。

## 3. 问题 1：预测尖刺

### 3.1 事实（file:line，已抽查）

1. **RTS 每批只保留最后一个包，时间戳取回调到达时刻**：RTS:1489 取 `lastPacket`，1505 `DecodeSnapshot(..., QueryQpc(), ...)`；1528 的诊断文本明确写着 `retained=1 timestamp=callback-arrival`。之后 C:17912–17916 只消费最新快照。模型看到的是“回调节奏下的稀疏位置”，不是均匀的硬件采样。
2. **采样间隔超过“预设帧间隔”就注入一次原地静止样本**：`ShouldStartEndpointSettling(sampleAge, 1/target_fps)`（SG:2167–2172）。阈值按预设算，与刷新率、笔报点率无关：240 预设为 4.17 ms，120 预设为 8.33 ms。满足条件且未收敛时，用最后位置和当前帧时间 `frameInputTime` 调用 `modeler.Update(stationaryInput)`（C:22308–22357）。
3. **下一个真实样本的模型时间**：`ResolvePenModelInputTime`（SG:2424）只保证不倒退，即 `max(real − offset, lastModelTime + 1µs)`。如果这个样本的 QPC 早于刚才注入静止样本的帧时间，它会被压到仅比静止样本晚 1 µs。
4. **Kalman 预测没有几何长度限制**：`kalman_predictor.cc:88` 用窗口平均 dt 把速度/加速度/jerk 分别除以 dt、dt²、dt³；连接段（connector）点数由距离与端点速度决定，没有总长度或时长上限（147–168）。
5. **预测点没有任何合理性检查**：`RebuildPredictedPoints`（SG:2513）直接把全部预测结果放进 L0，不检查是否有限、路径长度或端点距离。下一帧重新预测并整体替换 L0，所以异常只会持续一帧。

### 3.2 推断的发生过程

中档偏快速度书写 → 某次 RTS 回调晚到或笔漏报一个包，采样间隔超过预设帧间隔 → 本帧注入“原地静止”样本，模型认为笔突然停住 → 下一个真实样本已经移动了一大段（时间间隔可能只有 1 µs 到几 ms）→ 预测器估出很大的速度/加速度 → 连接段和外推冲出去，形成“尖刺” → 后续样本恢复正常，下一帧预测被替换，看起来“又对了”。

- 与症状吻合：偶发、与速度相关、只持续一帧、方向沿运动方向。
- **会话 2（240 预设）的阈值只有 4.17 ms**，与常见笔报点间隔（约 4–7.5 ms）重叠，理论上触发会更频繁。请确认：两次会话里尖刺是否在 240 预设下更常见？
- 尚未证明：日志里没有逐帧预测记录，以上是由代码推出的最可能机制，需要一次带诊断的复现来确认。

### 3.3 与阶段 A 的关系

- 预测、几何、RTS 文件在 A 中没有改动（Codex 比对两次提交的文件对象确认）。
- A 在输入 Drain 之前加了等待，会改变“哪些包被合并、帧时间与包时间的先后”，所以**可能改变发生率**。但这个机制在 A 之前就存在；要判断 A 有没有让它变多，只能用开关做 A/B 对比（性能页“waitable 模式下启用等待”）。

## 4. 问题 2：卡顿

### 4.1 能确定的

- **A 的等待不是长卡顿来源**：两次会话最长等待 28 ms，超时总共约 13 次；理论上最长 200 ms，但本次没有出现。
- **AutoSave 不是**：清屏时在绘制线程上的捕获耗时 0.4–5.6 ms；数秒后的 commit 在工作线程。
- **鼠标钩子嫌疑低**：`WH_MOUSE_LL` 在独立线程（`MouseHook.cpp`），移动消息直接链传，不取业务锁。

### 4.2 候选（按可能性排序，均为推断）

1. **“墨迹 + 鼠标一起卡”= 系统级（DWM/GPU）卡住**。系统光标冻结通常意味着 DWM 合成或 GPU 调度被拖住。可疑来源：
   - 悬停帧约 900 次/秒的 `Present1`（§5），持续给 DWM 送帧；
   - 整屏分层窗口更新：切到选择/演示输出时，`DrawpadPresentation` 做 2880×1920 的同步读回 + ULW（P:603–660），同一时刻 UI3 的 ULW 耗时 42 ms；
   - UI3 主栏 WARP 后端 `GetDC` 30–78 ms（`Bar.RenderLoop.cpp` 12218/12231）。
2. **“只有墨迹卡”= Draw3 绘制线程被占**。可能路径：同步的历史恢复/逐 tile 重放（C:19185、19882、21572；`Draw3.InkHistoryGpu.cpp:1370–1525`），后台 tile 预建在单个 tile 内不响应输入（C:22078），以及会话 1 14:04:25–26 那段 GPU 变慢。
3. 重连等待、橡皮空闲等待、输入准入都可被唤醒或只是拒收，不会无条件阻塞线程。

### 4.3 要定位需要的诊断（最小增量，未实施）

- 一帧耗时超过 32 ms 时写一行 Debug 日志，列出各阶段耗时：等待、输入/模型、历史/合成、Present、Map/ULW。现有 `metricsState_` 已经在统计这些阶段，只缺触发输出。
- 系统光标冻结时，另需 ETW（GPU/DWM 调度）才能确认，这一项靠应用日志无法证明。

## 5. 新发现：悬停帧不限速

- `drawingCursorRequested`（C:21520）在每次鼠标/笔悬停移动时置位；只有光标变化的帧在帧尾不命中任何 `WaitForFrameDeadline` 分支（C:23525–23605），渲染并 `Present1` 后立即进入下一轮。
- 结果：帧率等于输入事件率（1000 Hz 鼠标约 1000 帧/秒）。DComp 下多余的帧会被 DWM 丢弃，但 CPU/GPU/DWM 仍然要处理；**ULW 下每次悬停都要做一次同步读回 + ULW**，代价更大，会直接影响阶段 B 的测量。
- A 之前就是这样，A 没有改变它。

## 6. 对“A/B 之间是否先修”与阶段 B 的初步看法（待你决定）

- 三项候选修复（预测保护 + 异常日志、悬停帧限速、长帧阶段诊断）改动都小，都是 A 之前就存在的问题。其中悬停帧限速和长帧诊断会影响 B 的测量基线，我倾向于放在 B 之前。
- 阶段 B 的几个关键点：
  1. **独立纹理（B1）**：ULW 模式不再创建交换链，Renderer 以无交换链方式初始化，`InkRenderer::Resize`（`Draw3.Renderer.cpp:578`）补一个无交换链分支。改动面小、无争议。
  2. **异步读回会带来“延迟与吞吐”的取舍**：现在的同步 Map 在 GPU 快的时候延迟最低；只有单帧 GPU 耗时超出帧预算时（4K、大橡皮）异步才有收益。候选完成方式：帧尾探测（每帧最多 2 次 `Map(DO_NOT_WAIT)`，GPU 快时延迟不变）/ 固定下一帧完成（最简单，但 ULW 上屏固定多最多 1 帧）/ 同步 Map + 提交线程（调研 §6.3）。
  3. 建议先用强制 ULW 在本机和 Win7 设备上采一次 `copy_map_ms / rows_ms / ulw_ms` 基线（现有像素诊断已有这些字段），再决定要不要做、做到哪一步。
  4. 辅助输出 SelectionUlw 建议保持同步，只改主画布 ULW。
