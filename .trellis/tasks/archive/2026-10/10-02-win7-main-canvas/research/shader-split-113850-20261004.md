### 结论与证据范围

未发现可静态证明的唯一生产 shader 缺陷。新采集确实补齐了独立 WARP 执行证据：`D:/Personal/Downloads/Win7-Diagnostics/20261004-113850-937/pixel-test.stderr.txt` 的 backbuffer/offscreen Clear 均全 16384 像素 BGRA=(64,32,16,128)，正式和关闭混合的四项 Cursor 均全零，四项均 VSInvocations=6、PSInvocations=1368，GetDeviceRemovedReason=0。此独立测试没有 ULW、dirty Copy、生产 frame gate 或 warmup，因此这些阶段不是该 WARP 四项失败的必要条件。

主会话的另一分工发现同一设备正常应用使用 VMware Hardware，出现非零 ink/cursor staging 像素。此报告只直接复核 WARP 自检，不重新统计普通应用。用户随后向主会话描述“几乎不能出现内容，都是切换到橡皮，画布才会刷新”；因此不能把 Hardware 非零采样扩大成硬件应用已经正常，也不能把独立 WARP 全零推广到这台机器的 Hardware。WARP 的 shader/data/write 故障与硬件正常应用的刷新/ULW 故障须分别取证。

推荐最小 WARP 分界：**保留生产 VS、t0/b0、目标和状态，增加诊断专用固定输出 PS + 真实输入字段 PS；再以单独 Cursor PS 做等式对照，所有改变仅限显式独立测试 renderer。** 同时复制并打印当前上传的 b0 48 字节和 t0 前 32 字节；不要先永久替换 buffer、blend、shader 或 swapchain。

### 1. 真实执行路径与中心数学

CPU上传（`RendererPrimitives.cpp:337-372`）为：t0[0]=(64,64,16,16)，t0[1]=(outlineWidth,1,0,0)，b0.width/height=128，shape=4，offset=0，color=(1,1,1,0.5)，operator=Draw，padding=outline RGB。默认 outlineWidth 以 actual appearance 为准，不用未经读取的数字代替；无论常规1px左右描边，在中心均落入白色填充。

VS（`inkVertexShader.hlsl:79-93`）把quad扩至[46,82]²；clip z=0,w=1，pixPos保持屏幕坐标。中心读回像素(64,64)通常对应PS中心(64.5,64.5)，local长度约0.707，半径16，因此 outer/inner coverage=1，outline=0，fillAlpha=1*0.5，alpha=0.5，Add=(0.5,0.5,0.5,0.5)，Retain=(0.5,0.5,0.5,0.5)。透明目标上的正式resolve与disabled blend都应得到白色约128 alpha。shape6的grip分支不影响此shape4用例的选择结果。

只读 FXC10.1 dumpbin 显示真实 PS：先 `add v4.z,0.5; ftoi` 计算type；Cursor用 `ige(type,4)` 和 `ige(6,type)`；随后从 v1.xy/v3.xy/v3.zw/v4.x/v4.y/v2.w 计算距离、coverage和alpha，最后 `ge(0,alpha); discard_nz`，输出o0.xyz/w和o1.xyzw。没有发现明显错误寄存器/缺少alpha输出。

**源码中的 isnan 早退不能照抄成实际执行故障点：** `inkPixelShader.hlsl:233` 的 p1/p2 isnan 条件在当前 compiled PS 指令中没有保留下来。它不是本次反汇编看到的 early discard。未在本研究判定编译器是否应当保留该检查，也不建议因此改变生产编译选项；已知有限输入不依赖该检查。

PS=1368仅说明调用发生，不能证明中心被覆盖或PS输出非零/未discard。36×36=1296是预计quad像素面积；不要把多出来的72次强行解释为已确证的具体helper/重复像素来源。Microsoft statistics文档只定义invocation计数，而discard指令文档明确即使继续执行，所有输出仍被丢弃。

### 2. 签名和插值核对：诊断shader必须保持布局

当前 compiled VS OSGN 与 PS ISGN 对应：

| 字段 | register/mask | 正式PS插值 |
| --- | --- | --- |
| SV_POSITION0 | 0.xyzw（PS实际用xy） | linear noperspective/system position |
| TEXCOORD0 pixPos | 1.xy | linear |
| TEXCOORD1 uv | 1.zw | linear |
| COLOR0 | 2.xyzw | constant/nointerpolation |
| VAL_START0 p1 | 3.xy | constant |
| VAL_END0 p2 | 3.zw | constant |
| VAL_RAD_START0 r1 | 4.x | constant |
| VAL_RAD_END0 r2 | 4.y | constant |
| VAL_TYPE0 shape | 4.z | constant |

重复同一PS_INPUT结构、字段顺序、类型和插值限定是最简单的兼容做法，但**必须再检查新compiled ISGN的register/mask及相关dcl_input_ps**，不能仅凭semantic同名认为已经匹配。Microsoft Signatures 文档强调相邻stage使用固定register位置，顺序匹配有意义。字段validator应实际使用全部字段，避免编译/精简改变对照所需布局；uv在当前Cursor VS由零初始化保持0，pos.z=0、pos.w预期1，也可纳入检查。

`nointerpolation`并非Win8新增功能：官方HLSL struct文档列为SM4及以后支持。此案SM5/FL11创建正常，不能从平台版本本身断言这些constant字段非法。正确签名仍只证明合同，不证明Win7 WARP实际传值。

### 3. 最小诊断设计与解释矩阵

只在 `RunRendererPixelTest` 的独立renderer使用临时PS对象，保持正式VS与正式DrawTransientDrawingCursor上传/绑定。通过替换该独立对象的 `pixelShader` 字段让正式函数绑定对照PS；保存/恢复字段和任何state，不能在正常应用插标记。继续先执行六个原始case和原退出判定，diagnostic case单独标注结果，不能靠对照成功把正式失败改成PASS。

建议优先顺序：

1. **b0/t0上传字节读回。** 复制当前已Unmap的b0全部48字节、t0已写两个槽的32字节到无bind/misc的STAGING CPU_READ buffer；t0可用明确非空byte BOX(0..32，top/front0、bottom/back1)，目标32字节。沿用EVENT/Flush/3秒GetData和DO_NOT_WAIT Map，报告每字段expected/actual及完整32/48字节匹配；只能证明资源内复制的数据，不等于shader stage已读到同值。不要读取t0未写剩余区，因为DISCARD后其内容未定义。
2. **constant-output PS。** 不接收input、不依赖资源，仅输出o0=(0.5,0.5,0.5,0.5)、o1=(0.5,0.5,0.5,0.5)，保持生产VS生成quad，先disabled blend、再正式resolve。分别核center/corner/非零数和实际绑定。该控制无需VS->PS字段linkage，但仍走光栅与写入。与现有clear共同区分“draw写入整体失败”与“正式PS读取/执行结果”。
3. **opaque字段validator PS。** 全部正式PS_INPUT + 正式48字节b0；绝不discard，alpha=1固定哨兵。RGB各自编码0..255错误bit组，例如R=shape/color/style，G=p1/p2/pixPos/uv/pos，B=PS b0字段。最少报告中心RGB码和所有alpha覆盖像素的错误码union，而不复用“白色alpha128”验收器。pixPos应与SV_POSITION.xy接近（epsilon例如1e-3），p1=(64,64)，p2=(16,16)，r2=1，shape4，color白/.5，r1/outline等于CPU实际expected；global constants全部按当前visual核。固定alpha保证“错误值”不会再次变成全透明，RGB=0的通过值仍为opaque黑，不用rgb_nonzero作为validator成功条件。若加入非有限判断，优先asuint指数位判断或明确保留的compiled指令，不以优化后已消失的isnan当作唯一证据。
4. **cursor-only PS（若本轮必须一次采齐）。** 复用同一结构、原Circle/Rectangle/Grip距离和fill/outline输出，保留o0/o1，去掉其它工具/texture/history分支；记录profile/hash/compiled签名。它是定位单一正式大PS执行/控制流差异的实验，不是授权生产replacement。先disabled blend再正式blend即可，不再复制全部backbuffer/offscreen组合；普通offscreen已足以回答此分界。

| 新结果（同WARP/同目标） | 可支持的定位 | 仍不能宣称 |
| --- | --- | --- |
| 上传字节不符/Map或EVENT失败 | buffer upload/copy/readback阶段，按first meaningful HRESULT继续 | VS/PS编译器根因 |
| bytes正确，constant disabled也零 | PS基本执行输出、raster/OM写入/actual-target或特殊draw-readback问题仍在 | 正式Cursor数学造成透明 |
| constant disabled成功，正式blend失败 | 同已知o0/o1下正式resolve相关行为 | 永久关闭blend就是修复 |
| constant成功，validator有alpha且错误bit | 正式VS的数据读取/输出、VS->PS插值linkage或PS b0读取有具体异常 | 单凭字节CopyPASS排除GPU读取；立即怪shader大程序 |
| constant成功，validator也全零 | validator自身执行/签名/写入的实验失败 | 字段正确或全部字段读零 |
| validator全部正确，cursor-only成功，正式PS仍零 | 正式大PS字节码/控制流/JIT/相关执行条件与精简程序有差异 | 已确定某条opcode或驱动缺陷 |
| validator正确，但cursor-only也失败 | distance/coverage/math/discard/output共同分段继续诊断 | 必然是正式大PS复杂度 |
| WARP对照成功，正常Hardware仍靠切工具刷新 | 独立GPU控制不足以解释普通应用；继续生产frame/dirty/ULW证据 | Win7桌面可见性已恢复 |

### 4. SO/MRT为什么留作下一层

使用实际VS资源创建 `CreateGeometryShaderWithStreamOutput`，输出19floats×6vertices，可以精确读VS生产输出并分离VS与PS插值；官方API允许把前一级compiled shader直接传入，因而不需要runtime D3DCompiler。但这新增SO buffer/declaration、GS/SO绑定/清理、等待读回和Win7 GS创建分支；creation必须独立记录HRESULT。若validator已全部正确，SO不能进一步解释正式PS与精简PS差异。本轮先用validator；仅在字段坏值需要区分VS输出与插值时加入SO。

production PS在disabled MRT同时读Retain，可区分“写出了zero Add但nonzero Retain”与“两个输出都未写”，但这会改变single-RTV/dual-source目标合同，且“两个都零”仍可能discard或写入失败。相比constantPS+opaquevalidator，它回答范围较窄，不建议同时扩大当前suite。

### 5. 交付和构建边界

诊断shader可在维护环境预编译SM5并嵌入独立byte数组header，Win7只CreatePixelShader；不引入Win7 d3dcompiler_47等新动态依赖，不重建/覆盖八个现有产品+Demo CSO，也不调整产品resource ID或vcxproj。这是诊断专用新增资产方案，须由主会话确认与“单一正式shader构建链”规范的适用范围，不把手工FXC产物混为生产shader。保存可复现HLSL/FXC配置、profile和hash，并核真实VS对应signature。

选择更小的纯existing-resource SO方案也合法，但不能仅以“没有新资产”替代决定性验证要求。只有研究结果，没有本机Win7故障复现；本机Win11对照PASS只能验证新探针可运行。正常Hardware刷新问题仍由主会话按完整日志调查。
