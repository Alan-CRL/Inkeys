# Research: Integrated Draw3 history, persistence and long-document cost

- Query: In the integrated product, which document/history/cache/save operations grow with stroke or page count, and how can they be measured without an HWND?
- Scope: internal
- Date: 2026-09-28

## Findings

### Document/history costs and ownership

1. `InkCanvas::AppendStroke` moves a stroke into a vector and returns an index (`Draw3.InkDocument.cpp:103-116`); `InkCanvasCollection::AppendPage` linearly checks every existing page GUID (`Draw3.InkDocument.cpp:173-182`). This is expected for a small number of pages, but building a large PPT page topology gives cumulative O(P²) GUID comparisons. `InkPage::FindCanvas` is also linear (`Draw3.InkDocument.cpp:126-146`), likely cheap with one default device.
2. Completed strokes are appended to `InkCanvas` **before** `BuildStrokeTileFootprint` and `CanvasRuntimeHistory::AppendStroke` (`Draw3.DrawingController.cpp:7437-7458`). `CanvasRuntimeHistory::AppendStroke` copies/normalizes tile vectors into its `CompositionRangeTree`, updates per-tile references and generations (`Draw3.InkHistory.cpp:902-933`, `661-682`); expected cost is primarily point/footprint count and touched tile count, not total document count. `BuildStrokeTileFootprint` scans all points and builds separate 128px undo and 256px composition tile lists, sorting/deduplicating each (`Draw3.InkHistory.cpp:469-506`, `583-610`). Measure its allocation and tail on long, slow, repeated-point, eraser and long-diagonal strokes separately.
3. Undo/redo flips visibility and tile reference counts but retains old `InkCanvas::strokes_`, `CanvasRuntimeHistory::items_`, `CompositionRangeTree::items_`, per-tile block/generation maps and before/after state arrays (`Draw3.InkHistory.cpp:949-993`; `Draw3.DrawingController.cpp:355-367`). A new stroke after Undo clears only `redoItems_` (`Draw3.DrawingController.cpp:7444-7448`); the no-longer-reachable stroke/history data remain until Clear or slot replacement (`Draw3.DrawingController.cpp:5486-5500`). This is a **confirmed resource trend**, not yet a quantified leak or permission to discard undo history. The 10/100/1000 stroke plus repeated Undo/new-branch benchmark must record bytes/item counts and compare visible strokes to retained history.
4. Cold replay falls back to per-tile range scanning and rasterizes matching visible items in order (`Draw3.InkHistoryGpu.cpp:753-825`, `1358-1510`). `CompositionRangeTree::DecomposeRange` may scan a full node range for barriers (`Draw3.InkHistory.cpp:827-899`), but the integrated completion path passes `affineOperator=true` (`Draw3.DrawingController.cpp:7451-7455`); no current controller call to `SetItemBarrier` was found. Do not treat barrier-heavy replay as a typical production regression without a reachable case. Page switching clears L2/transient layers and requests restore of the new page (`Draw3.DrawingController.cpp:6243-6258`), so cache hit/miss and ordered replay must be measured on alternating page identities.

### Cache bounds and CPU overhead

5. Undo policy is 64 MiB, at most 20 entries, 1024 tile slots of 64 KiB; composition policy is 192 MiB, 512 slots of 384 KiB (`Draw3.InkHistory.cppm:18-37`). GPU storage grows lazily in texture-array pages and is evicted according to planners (`Draw3.InkHistoryGpu.cpp:304-340`, `442-485`, `920-977`). `DiscardHotPreimages` and `DiscardCompositionCache` release their pages on page/clear/device transitions (`Draw3.InkHistoryGpu.cpp:1349-1356`, `1540-1547`; controller `5498-5500`). These budgets cover the cache textures, **not** CPU document/history/snapshot allocations or all renderer resources. Allocated arrays may remain resident after individual LRU eviction until discard/repack; use actual process private bytes/GPU residency, not only planner resident count.
6. `CompositionCachePlanner::Acquire` looks for an existing key linearly, then for each candidate free slot scans all resident entries (`Draw3.InkHistory.cpp:1290-1338`): on a miss near its 512-slot default capacity, the free-slot search is O(C²) comparisons. GPU-side `FindResident` is another linear lookup (`Draw3.InkHistoryGpu.cpp:828-832`). A bounded planner microbenchmark should record miss latency and comparisons/allocations at 0, 128, 384, 511 and 512 occupied slots; measure actual page-switch/replay cache miss frequency before changing representation. The CPU cost is **inferred**, not measured here.

### Save capture, queue and page identity

7. Desktop Clear/exit capture iterates every history item, deep-copies every visible stroke's points on the **drawing thread**, then submits a value snapshot (`Draw3.DrawingController.cpp:1689-1767`). This is O(total stored history items + visible points) even though UInk encode/I/O is on the worker. Repeated desktop Clear creates a separate accepted FIFO request and retains its full snapshot until worker completion (`Draw3.AutoSave.cpp:855-903`, `998-1038`); there is no byte/count admission cap on accepted snapshots. `diagnostics.queuedSnapshotBytes` measures this queue (`Draw3.AutoSave.cpp:1026-1031`), and completion releases the large snapshot (`:980-988`). An I/O slowdown can therefore grow queue memory; dropping accepted saves is forbidden by durable-save semantics, so any backpressure change needs a separate design and latency evidence.
8. `DesktopAutoSaveService::records` retains one lightweight identity per accepted request even after the snapshot is released (`Draw3.AutoSave.cpp:855-864`, `998-1038`); this may grow over a long session with repeated Clear. The queue and `CloseAndDrain` are FIFO and join the worker (`Draw3.AutoSave.cpp:884-903`, `1154-1162`); no hard timeout or accepted-request abandonment was found in this path. `UInkReadLimits` caps a file at 128 MiB, model charge 256 MiB, geometry points at 4 million and single geometry at 1 million (`inkStrokeModelerTest/draw3/uink_model.cppm:424-436`), which bounds disk import per file but not all in-process snapshot copies.
9. Presentation capture walks **every active page and every history item** on the drawing thread, deep-copies visible points, then duplicates `activeCanvases` into legacy `canvases` (`Draw3.DrawingController.cpp:4694-4780`). On each page switch, `capturePresentationAutoSave` runs when mutation revision is dirty (`:4813-4838`, `:5823-5825`, `:6243-6244`). Across a growing document with one stroke + switch per step, cumulative capture work is O(N²) in total strokes/points. The snapshot duplicate is an exact additional copy; exporter uses active/retained when present (`inkStrokeModelerTest/draw3/uink_draw3_export.cpp:34-55`), but the compatibility reason for keeping legacy field must be reviewed before removal.
10. Presentation worker coalesces only pending non-Clear tail requests for the same key; Clear boundaries remain FIFO (`Draw3.PresentationAutoSave.cpp:1121-1152`). `MergePresentationSnapshot` copies the request snapshot, linearly searches canonical active/retained pages for **each** requested page, then copies merged active to legacy canvases (`Draw3.PresentationAutoSave.cpp:578-625`). This creates O(P²) GUID comparisons per save plus multiple full-document copies. It is a good isolated CPU benchmark candidate before changing page lookup, while preserving stable SlideID and EndScreen identity. The worker's full UInk export is production shared logic (`:672-679`), and save uses a named mutex/index, so disk timings must be separated from capture/merge/encode.
11. Draw3 holds independent Desktop/Whiteboard/PPT document slots and a map keyed by presentation identity (`Draw3.DrawingController.cpp:1595-1611`, `:4612-4629`). Parked PPT slots can be evicted only under `ShouldEvictPresentationSlot`; this is a data safety gate, not an arbitrary LRU. Long sessions with many presentations need `presentationSlots.size()`, retained-slide bytes, pending/committed revisions, and page identities captured. Do not cap these by dropping dirty slots.

### Correctness/safety item for separate validation

12. There is a **confirmed non-atomic internal append sequence**: `InkCanvas::AppendStroke` accepts any finite nonnegative width/finite coordinates (`Draw3.InkDocument.cpp:32-37`, `:103-116`), while `BuildStrokeTileFootprint(stroke)` without visible fallback rejects representational overflow or unquantizable tile range (`Draw3.InkHistory.cpp:522-573`, `:583-605`). A finite `StoredInkPoint` near `FLT_MAX` with large finite width can pass `InkStroke::IsValid` but fail the footprint. In the live completion path the document stroke remains appended while history append is skipped (`Draw3.DrawingController.cpp:7437-7458`, `:7567-7572`), so future document/history indices can diverge. UInk materialization builds a **temporary** page/slot and rejects on footprint failure (`Draw3.DrawingController.cpp:4872-4895`, `:4995-5018`); do not claim external-file data corruption from that path. Reachability from real input and exact subsequent effects are **not verified**; first add a production-module pure CPU boundary test, then test the transaction boundary before assigning severity/fix. Possible minimal shape: compute footprint before the authoritative document append, or roll back only the just-appended stroke if history append fails, without changing GPU-failure authoritative behavior.

## Reproducible no-HWND measurement proposal

1. Add an opt-in benchmark to an existing console test target, explicitly linking `Inkeys/Inkeys/Drawing/Draw3/Draw3.InkDocument.cpp[m]` and `Draw3.InkHistory.cpp[m]` production modules. Do **not** benchmark `inkStrokeModelerTestTests/ink_history_tests.cpp` as if it were integrated history: its vcxproj links the standalone `inkStrokeModelerTest/draw3/ink_history*` files. If using `InkeysHeadlessTests`, register module source and test in its existing vcxproj/filters and run `--no-window`; do not instantiate `DrawingController` or create HWND. The shared UInk converter may be linked to the existing console suite separately for snapshot/merge.
2. Deterministic cases per 10/100/1000 strokes: (a) 1-point tap, (b) 64-point curved pen, (c) 64-point eraser crossing prior ink, (d) 1024-point slow/overlapping pen, (e) 1000× Undo→new-stroke branch, (f) 10/100/1000 PPT pages with distinct Page GUID/SlideID and separate EndScreen, alternating page identity. Use fixed points/widths/colors and identical input order for H0 and HF. Assert item/stroke/visible/redo counts, tile footprints, unaffected page identity, and deterministic content digest before timing.
3. Separate timers for `InkStroke` validation and `InkCanvas::AppendStroke`, `BuildStrokeTileFootprint`, `CanvasRuntimeHistory::AppendStroke`, Undo/Redo, `VisibleCompositionTiles`/`DecomposeRange`, and planner acquire/hit/evict. For persistence, separately time production snapshot capture logic **if extracted behind a production callable function** and `MergePresentationSnapshot` (currently an anonymous-namespace function inside the production .cpp); avoid reproducing these algorithms in test code and calling that a product benchmark. Record process private bytes/working set, allocation count or ETW heap if available, stroke/history/map sizes, queue estimated bytes, cache capacity/residents/evictions and three warm-up plus at least three measured rounds with median/P95; do not present P99 from tiny samples.
4. For disk tests, use an isolated temporary AutoSave root and real `DesktopAutoSaveService`/`PresentationAutoSaveService`, fault-inject worker delay through existing explicit test injection only, submit 10/100/1000-stroke snapshots, call `CloseAndDrain`, verify each accepted request completion and last durable UInk/index identity. Keep these results separate from pure CPU timing and from GPU/visible Present. No product window, RTS or GPU is exercised; FL11.0 hardware/WARP, Win7 SP1+KB2670838, DComp/ULW and FLIP require their own target-machine matrix. Preserve FLIP per the user-observed Win7 contract.

## Caveats / Not Found

- No build, benchmark, GUI or performance sampling was run in this read-only research role; all cost classifications above are code-derived until measured.
- This report does not establish Down→successful Present latency, GPU residency, optical latency, real Win7 hardware/WARP behavior or save throughput on a slow disk.
- No evidence was found that the currently integrated controller invokes `SetItemBarrier`, or that a normal pen/device can actually produce the extreme-but-finite footprint failure; both require targeted production tests before release severity is set.
- Snapshot merge is private inside the production persistence module; a measured standalone reimplementation would not count as product evidence. Expose a narrow production callable for benchmarking only if an existing test seam cannot exercise it through the service.
