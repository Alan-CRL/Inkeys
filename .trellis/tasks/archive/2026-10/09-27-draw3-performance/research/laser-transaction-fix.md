# F-025 Laser raster/bake transaction implementation

## Change boundary (2026-09-28)

- Current gap: full Laser redraw ignores failed coverage/resolve, and bake releases its only CPU points after a failed pass. A partially baked source-over layer cannot be retried onto the same compositor without darkening overlap.
- Owner: the Draw3 drawing thread. `DrawingController.cpp` owns the CPU layer lifetime and frame success gate; `RendererLaser.cpp` owns synchronous D3D pass results; `Renderer.cpp/.cppm` owns size-dependent resources. `HiddenWindowTest.cpp/.h` owns the explicit no-HWND CLI test.
- Transaction design: lazily create one RGBA8 scratch compositor at the current viewport size. Copy the committed compositor into it before each bake, rasterize the whole pending batch into scratch in original Down order, and publish it by swapping resource owners only after every checked pass succeeds. Failed scratch remains unpublished; a retry starts from the committed compositor again. Extra GPU allocation is exactly one 4-byte-per-pixel viewport texture plus its RTV/SRV (about 7.9 MiB at 1920x1080, 31.6 MiB at 3840x2160). The existing live coverage still contains the current incremental contact at Up; L2, trusted snapshot and backbuffer have other owners and cannot safely be borrowed as bake scratch.
- The targeted test uses the production bake helper and shaders on a WARP FL11.0 device with a composition swapchain that has no HWND. It swaps in a valid DEFAULT non-CPU-writable structured buffer after the first layer, so the second production `Map` fails. After restoring the writable buffer it compares a 64x64 BGRA backbuffer readback byte-for-byte to the clean two-layer sequence. The test path is explicitly requested by CLI; no normal product input can trigger it.
- Not within this change: Laser dots/particle errors, asynchronous GPU execution errors, optical display, Win7 real device verification, UI3 device, swap effect, DComp/ULW routing, persistent ink, or a new presentation mode. Existing successful bake discards CPU geometry, so device loss during Hold/Fade requires separate bounded retention/rebuild design and verification before declaring that path closed.

## Applied behavior

- `InkRenderer::BeginLaserBake/LaserBakeTarget/CommitLaserBake` owns one lazily allocated RGBA8 scratch. On every batch it copies committed `laserCompositedColor` into scratch and exchanges owners only after all coverage/resolve passes report success. Resize and lifecycle clear release the scratch; no change to the FLIP swap effect, renderer device ownership, or DComp/ULW selection.
- `BakeLaserStrokeLayers` now returns a result, defers committed bounds and CPU layer release until commit, and retains the original Down order after a real Map failure. The first-layer-success/second-layer-failure case retries from the untouched committed compositor, so source-over is not applied twice.
- Full Laser redraw checks local clear, coverage upload, and resolve results. Stable color resolve reports failure. `DrawingController::Run` carries these failures to `rasterSubmissionFailed`, suppressing that frame's Present/readiness transaction; the existing bounded raster retry loop retains input. Same-frame old Up → new Down accepts the new contact while retaining the failed old CPU batch for full redraw.

## Remaining limits

- Previously **successful** baked batches still release their CPU geometry. A device-lost recovery during Hold/Fade clears GPU `laserCompositedColor` and cannot reconstruct that already committed transient Laser trail. This is a separate P2 visual continuity risk; the tested transaction only protects batches that failed before commit. Retaining all accepted Laser geometry for the whole configurable Hold/Fade (up to 24 hours) has no current bounded memory policy, so it was not added speculatively.
- `DrawLaserDots` and particle draw are still void best-effort paths; asynchronous GPU execution/device errors surface at later device/Present boundaries, not through the synchronous bool checks. The no-HWND test proves actual WARP FL11.0 D3D submission/readback and exact BGRA retry on this Win11 ARM64 machine, not UI/ULW/DComp success, optical latency, hardware GPU, or Win7 SP1 + KB2670838 behavior. Win7 Hardware FL11.0 and Hardware→WARP fallback remain separate manual gates, with FLIP retained as required.
