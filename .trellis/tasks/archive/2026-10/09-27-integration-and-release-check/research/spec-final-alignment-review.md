## Findings (not fixed)

- **P1，退出 spec 对双重监督建立失败过度承诺。** `errors-logging-and-resources.md:125-139` 写首次正式请求建立 15 秒监督、helper 失败由自身兜底且到期无条件结束旧进程。正常代码 `IdtMain.cpp:256-278` 的确 CAS→`BeginShutdown`→`ArmShutdownSupervisor`→`offSignal`→异步隐藏/唤醒；`Window.cpp:211-215` 的 BeginShutdown 仅原子存储，不等 owner。可是 `ShutdownSupervisor.cpp:297-301` 的自身兜底 `CreateThread` 可能失败，helper 建立/握手也可能失败，`:384-386` 会返回 `ArmResult::Failed`；`IdtMain.cpp:274-275` 明确记录“15 秒保护未建立”而继续清理。此时若清理卡住，旧 PID 无本次 15 秒 owner。规范应把 `Armed/FallbackArmed` 的有界保证与 `Failed` 的无保证边界分开，并在矩阵加入双重建立失败；若用户决定要求任何正式意图都强退，则需另有失败时直接结束旧进程的产品实现与隔离测试，不能用现有单 helper 失败绿测宣称双重失败通过。
- **P2，设置页直接按钮的 Arm 前序未在 spec 说明。** `errors-logging-and-resources.md:114,121,125,143,159-160` 把设置直接按钮和 `QueueClose/QueueRestart` 描述成点击即经全局入口。实际 `Setting.cpp:1576-1590` 的两个 ImGui 按钮先调用 `Setting::Hide()`，再调 `RestartProgram/CloseProgram`；`:8539-8549` 的 Hide 在 Arm 前取 `settingStateMutex`、向 `SettingBusinessQueue` 入队并唤醒渲染。`QueueClose/QueueRestart:458-467` 本身直调全局入口，但当前文件只有定义，无直接按钮调用。业务 worker 在 `Setting.cpp:167-180` 取走命令后释放 FIFO mutex 才执行 I/O，故“旧 worker I/O 卡住”本身不会一直持有 Hide 的 FIFO 锁；现有证据不能断言该场景违约。仍应将实际点击路径及 Hide 的短锁/入队前奏写明，测试要命中按钮而非只调用 Queue helper；若要求从确认点击起对**任何**设置锁卡死都开始倒计时，当前顺序不满足该绝对表述。
- **P2，UEF 与正常 SetOffSignal 意图需分流描述。** 同一退出 spec `:114-125` 包含“程序自身故障收尾”，但 `SetOffSignal` 的 1/2 是正常 Close/Restart；真实 UEF 在 `CrashHandler.cpp:477-511,649-671` 用 `TryClaimCrashRestartIntent` 抢 `offSignalInterop=3`，mode0 等确认、mode1 早抢、mode2/3 另有可取消报告截止，未统一进入 `SetOffSignal`。目前 `Tests Required:149` 虽把真实 RaiseException 单列，合同正文仍容易将普通 15 秒退场/Window gate 套到所有崩溃模式。建议明确 UEF 的单独报告阶段、mode1/手动确认的 restart intent，与正常 1/2 入口共享监督原语但有不同触发时点；模式 0/2/3 的报告保护不能冒充已经 Arm 的正式重启。
- **P2，Contact 诊断计数的 Reset 语义缺失。** 新 `input-and-ink.md:431,452` 说明 `ResetForNextRun` 清 route/freeMask，也列 `inputDownPublished/recycled` 为资源诊断，却未写两计数**不会随 Reset 清零**。`ContactInput.cpp:1053-1079` 只重置 route/队列等，`:681-686,1157-1174` 的诊断累计值持续存在；`Host.cpp:1041-1045` 跨 RunMode 重用它们。这正是本轮 Win32 测试曾把全局 `downPublished==recycled` 当空槽而产生的静态假失败风险。规范应要求跨 Host generation 用本轮基线增量，若需当前真实槽数用 `occupiedSlots`；不把全局累计差当作 Reset 后的路由占用。
- **P2，Contact Scenario 的页切换 Good Case 比测试要求更强。** `input-and-ink.md:446` 说 Close 被暂停时普通页切换继续处理其它命令；`:450-453` 要求真实 `ContactInputCoordinator` CAS hook、Controller Laser helper、Hidden Host，却没有要求在**生产 Controller 的普通页切换调用点**注入该 Closing。源码 `ContactInput.cpp:858-880` 的非阻塞 CAS 局部合同有真实 headless 红绿证据，`DrawingController.cpp:6325,6371-6386` 的其它拒收/页边界调用仍需要独立的整链门，不能用状态机单测替代“页切换继续”的产品结论。建议将该生产交错列入 Tests Required，或把 Good Case 限定为 Discard 调用本身有界。
- **P3，同一 errors spec 旧节的 API 名称与本次退出链不一致。** `errors-logging-and-resources.md:71` 仍写 `RenderScheduler::Scheduler::WakeForStop()`，而实际入口为 `IdtMain.cpp:270` 的 `Inkeys::UI::RenderPipeline::WakeForStop()`，定义见 `RenderPipeline.cpp:896`；新增 `:125` 只说唤醒 UI3 scheduler。应同步旧 Signatures，防止按不存在的名字实现或审计。它是 spec drift，不是本轮源码故障。
