# 批注画布冻结与退出不退：生产调用链只读调查

日期：2026-09-28。根据主审转述的用户图片/文字症状调查：批注画布突卡、光标可见但无新墨迹、选择模式不撤画布、Clear 无效、Bar/设置仍响应、桌面被画布遮挡、点击退出有反馈而进程不退。本人未取得现场进程栈、时间线、日志、presenter 模式、设备/输入类型，也没有运行 GUI、构建或性能采样；**不把截图当作根因复现**。本报告只写真实代码链与可验证假设，未改产品代码或父账本。

## 同时解释多种症状的两个条件性 P1 活性缺口

| 条件与精确链 | 可确认的卡住点 | 现场尚缺的证据 |
| --- | --- | --- |
| **控制标记入队失败后业务桥接不一定再被消费。** Bar/Setting 的 `PublishProductState`/`PublishProductCommand` 经 `Host::PublishState/PublishCommand` 更新 bridge，随后调用 `input.PublishControlWake()` 却忽略返回（`Draw3.Host.cpp:1614-1623,1655-1660`）。`ContactInputCoordinatorImpl::PublishControlWake`（`Draw3.ContactInput.cpp:347-359`）先 `SignalWake` 递增 generation/SetEvent；若 `queue.try_enqueue(controlProducerToken,nullptr)` 失败则清 pending 并返回 false。Controller 的 `processCommand(record)` **仅在 dequeued record 为 null** 时才 `observer_.controlWake`→`Host::ConsumeBridge`→`PumpBridgeCommands/PumpBridgeState`（`DrawingController.cpp:4717-4725`、`Host.cpp:1015-1024`）；等待被 generation/event 唤醒，本身不会 pump bridge。`WindowController::QueueCanvasCommand` 和 `SetSelectionMode` 的控制唤醒失败也被忽略（`WindowControl.cpp:394-397,438-443`）。 | 如果控制 token 入队失败且后续没有另一次成功控制标记，已接受的 Clear/工作区命令、选择快照可滞留；画布窗口仍沿旧 runtime ready/visibility。退出时 `Host::Stop` 用 `bridge.StopWithFinalCommand(PrepareExitAutoSave)`，再 `stylus.Shutdown()` 与一次同样可能失败的 `input.PublishControlWake()`（`Host.cpp:1320-1329`）；`exitAutoSaveCondition.wait` 无超时，仅等 `exitAutoSavePrepared || !running`（`:1329-1336`）。绘制线程若仍运行且从未取得 null marker，final command 不会变成 CanvasCommand/回执，Stop 可无限等。队列预分配 256 或 `slotCapacity+1` 且 `try_enqueue` 明确可失败（`ContactInput.cpp:303-307`）；**失效分支是代码事实，现场是否真的入队失败未知**。如果 producer 后续补发成功 marker，可能自行恢复，故不是“任何队列满必永久停”的断言。 | 事发时 bridge revision/accepted command sequence、control enqueue 成功/失败、wakeGeneration、null marker 消费计数与 `clearCommandCount`。现有 `ContactInputDiagnosticsSnapshot` 的 `controlWakes` 只在 `EnableDiagnostics` 时计数，而产品 Host 默认仅隐藏测试启用（`Host.cpp:1067`），不能把生产快照中的 0 当成没有 control wake。若线程栈在 `Host::Stop` 的 `exitAutoSaveCondition.wait`，且 `running=true`、bridge final 待消费、输入队列无 marker，最支持此链。 |
| **退出信号排在无界窗口同步等待之后。** 设置页 Close business worker 调 `CloseProgram`（`Setting.cpp:251-256`）；Bar 退出确认也调它（`Bar.Interaction.cpp:3344`）。`CloseProgram`/`RestartProgram` 先 `WindowService.HideAllUserWindows()`，返回后才 `CrashHandler::Shutdown`、`SetOffSignal(1/2)`（`Helper.CrashHandler.cppm:57-71`）。HideAll 依次对 overlay group 的 Bar、setting group 的 Setting 发同步 `Submit`（`Window.cpp:317-322`）；跨 owner thread 的 `Submit` 入队后无超时 `future.get()`（`:1121-1141`）。 | overlay owner thread 持有 Drawpad/DrawpadPresentation/Bar/Freeze/PPT 等 HWND（`Window.cpp:798-809`）；如它陷在 WndProc、`ShowWindow`/`SendMessageW`、样式或绘图同步调用，设置 worker 会卡在第一个 HideAll 的 `future.get`，`offSignal` 从未发布，主循环继续，Draw3 可仍运行且旧画布可见。若设置 owner thread 阻塞，则 overlay 可能已隐藏，但同样未发布退出。此为明确的**条件性**等待环入口，不能仅凭 UI 按钮出现反馈证明 `CloseProgram` 已抵达 `SetOffSignal`。 | 退出按钮来源（Bar/Setting）、`offSignal` 是否置位、Setting business worker/Window overlay 与 setting owner 的线程栈、Window Service 命令队列及 `HideAll` completion。Bar/设置帧仍渲染只证明共享 UI RenderPipeline 活着；Window Service owner 线程、Draw3 线程是另外的 owner。若栈在 `Window::Submit::future.get` 且 `offSignal=0`，则是此链而非 AutoSave worker drain。 |

这两个缺口可以叠加：Draw3 消费者本来因其它故障停滞，随后退出在 HideAll 或保存屏障上放大为不退。它们都是需要单独故障注入的 P1 **条件性**活性风险；目前无法按截图确定最初事件。

## 其它匹配路径与排除信号

1. **producer 光标独立于权威墨迹。** RTS `StylusDown` 先 `PublishPenCursor`，后 `coordinator_.PublishDown`，后者失败会返回 `E_OUTOFMEMORY`（`Draw3.RealtimeStylus.cpp:1193-1221`）；`Packets` 即使 `PublishMove` 失败仍 `PublishPenCursor`（`:1347-1361`）。Window WndProc 的 Mouse cursor mailbox 亦由 `WM_MOUSE*` 独立发布，`RequestDrawingCursorRender` 只发控制唤醒（`WindowControl.cpp:799-866,1555-1730,922-925`）。因此“有光标”可能只是系统箭头、最新 producer sample 或旧 app cursor；**不能推出 Down 已接受、Controller 在推进或 Present 成功**。若用户看到持续随笔移动且正确重绘的 app cursor，则绘制线程完全卡死的解释会变弱，需确认它是何种 cursor。
2. **活动 contact 严格阻塞画布命令。** `processCanvasCommands` 只有 `active.empty()` 才出队（`DrawingController.cpp:6550-6562,7793-7799,8743-8745`）；Clear、SetWorkspace、PPT target、`PrepareExitAutoSave` 均在该 FIFO。未收到/未消费 Up 时 active 不会因静止自动失效，Clear 与场景切换可一直不执行；`ReadSetting`/Bar仍可动。`Stylus::Shutdown` 正常会 `CloseAllProducerContacts` 发布 Cancelled（`RealtimeStylus.cpp:2615-2651`、`ContactInput.cpp:781-809`），Controller 的终态处理和 ended erase（`DrawingController.cpp:7909-7952,8641-8687`）应最终清 active；若 producer/consumer 正好停在 writer latch、RTS disable 或模型/GPU 调用，这一恢复条件失效。此链解释 Clear、选择 ready 和退出屏障，但不是仅凭截图可证的“丢 Up”。`CloseAllProducerContacts` 的 `ReadSnapshot` 连续不可读时在 `YieldProcessor` 重试无超时，`Close` 的 writer latch 也是无界等待（`ContactInput.cpp:225-239,493,793-805`），应在故障注入里观测，而非擅自释放持有者 latch。
3. **持续 raster/Present 失败与真实线程阻塞不同。** 普通光栅提交失败当前不发布空白 Present，CPU contact 保留、限频 `[Draw3.Raster] submission failed` 日志，idle 最多约 250 ms 后尝试重建（`DrawingController.cpp:8887-8915,8971-8978`；F-023）。Present 失败设置 recovery pending 且请求下一帧，恢复失败则保存已完成内容、`window.RequestExit()` 并 break（`:2731-2747,7333-7367`；F-026/F-027）。Host Run 返回后会销毁 controller 并置 `running=false`（`Host.cpp:1197-1226`），主循环每约 100 ms 检查 `ProductRunning`，意外停止时发布 offSignal 并成对 Hide（`IdtMain.cpp:2585-2614`）。所以长时间画布可见+进程活着，若不是主线程/Window owner 也被卡住，更像 Host **仍 running 但绘制线程在某个阻塞调用内**，而非完整 fatal 返回；具体 GPU driver `Present/Map/ULW` 是否卡住只能用现场线程栈判定。反复恢复仍在进行时应有失败日志/`presentCount` 变化，持续失败不能被单张静态图片认作死锁。
4. **选择模式显示语义。** `ResolveDrawpadPresentationSurface(selectionMode, currentPageHasContent, auxiliaryFullFrameClean)` 在 selection + 有内容或辅助全透明尚未验证时仍选 `Presentation`，只在空内容且辅助帧已净才选 `Hidden`（`Draw3.PresentationState.h:14-21`）。`IdtState::ReconcileDraw3PresentationState` 还等待 `requestedOutputTarget/revision == readyOutputTarget/revision`、`presentedContentRevision == contentRevision`，若绘制线程不再成功 Present 会持续 Waiting（`IdtState.cpp:438-501`）。因此“切选择不隐藏”需区分旧主窗确实可见、辅助窗按合同可见、辅助 alpha 错误挡背景、以及 Window Service 命令失败；Window Service 的配对切换会读回两窗可见性，失败时尝试双隐藏并打低频日志（`Window.cpp:1653-1733`）。主栏/设置正常不验证这些窗口状态。
5. **若 offSignal 已置，退出后仍有多个独立无界点。** 主清理先 `Setting::Shutdown()` 和若干 `jthread.join`，后 `StopProduct`，再 `WindowService.StopAndJoin`（`IdtMain.cpp:2672-2687`）。`Setting::Shutdown` 对 RenderPipeline `PostControl` 返回 true 后无限等 `settingDrainCondition`，RenderPipeline 正常退出会取出已接受 finalTasks（`Setting.cpp:8495-8523`、`RenderPipeline.cpp:650-663`），但 render callback 真卡住仍会阻塞。`Host::Stop` 退出屏障之后顺序 `DesktopAutoSaveService::CloseAndDrain`、`PresentationAutoSaveService::CloseAndDrain`，两者 `worker.join` 无硬超时；各自索引 named mutex `WaitForSingleObject(INFINITE)`（`AutoSave.cpp:269,1154-1162`、`PresentationAutoSave.cpp:141,1188-1195`）。这些与“退出不退”兼容，通常不单独解释**退出之前**无墨迹/Clear。必须用 offSignal 与线程栈定位，不用强行加入保存超时而丢已接受请求。

## 低开销分辨与无 HWND 复验切口

| 要观察的边沿 | 现有生产字段/日志与解读 |
| --- | --- |
| 命令是否只到 bridge | 在触发一次 Clear 前后记录 `PublishProductCommand` 返回、bridge sequence/revision；再读 `HostRuntimeSnapshot.clearCommandCount`（`Host.h:186-235`、`Host.cpp:1378-1453`）。accepted 增而 clearCount 不变，结合 control marker 成败/activeCount 才能区分未 pump 与被 active gate 延迟。现有 Host snapshot 含 `running/firstFrameReady/presentCount/successfulPresentCount/lastPresentSucceeded`、workspace/selection、requested/ready output revision、content/presented revision；快照内有两处 mutex，**不能**在疑似锁死的主线程无限调用，应另加只读原子健康小快照或用受限诊断线程采集。 |
| 帧是否还提交 | 动笔/切选择时 presentCount 不变但 UI3 帧继续：绘制线程没到 Present，查线程栈、`active` 与控制标记；presentCount 增而 successfulPresentCount 不增：Present 失败/恢复；两者增而 Clear count 不动：命令 admission/active gate。`runtimeRevision` 只在若干业务边沿推进，不是每帧 heartbeat，单独不动不等于死锁。生产 contact 计数只在显式 `EnableDiagnostics` 时累积，默认 0 不可作断言。 |
| 可见性与退出阶段 | 读 `WindowService` 两 HWND 的 `IsWindowVisible`、owner thread id/capture、`[状态线程][ReconcileDraw3Presentation] surface 切换失败`、`[PptExitSurface]` 与 `[Draw3] drawing loop stopped`、`[Draw3.Raster]`、`Present failed`、`[Draw3.AutoSave] action=exit_barrier`、`[主线程][IdtMain] Draw3 Host 意外停止` 现有记录。`offSignal=0` 且 worker 栈 `future.get` 指向退出隐藏前门；`offSignal≠0` 且 Host 栈 `exitAutoSaveCondition.wait` 指向控制/active 屏障；保存 worker/named mutex 栈则是更后阶段。日志缺席本身不证明阶段。 |

**无 HWND 故障注入建议。** `ContactInputCoordinator(size_t slotCapacityForTesting)`、`PublishControlWake`、`CaptureWakeGeneration`、`WaitForWake`、`TryDequeue`、`AcknowledgeControlWake`，以及 `StateBridge::Publish/StopWithFinalCommand/TryConsume` 都是真实生产 API。加测试专用的一次性 control-token enqueue 失败点（不影响 contact enqueue），先捕获 generation，发布 Clear 或 final command，强制 `PublishControlWake` 返回 false，断言 `WaitForWake(oldGeneration, boundedTimeout)` **确实返回 true**、`TryDequeue` 可读尽旧数据却无 null，再证明桥接命令不能仅凭 event 被 Host pump；此为源码红灯。修正后在相同真实 API/生产消费入口断言 Clear、Selection state、Final exit barrier 各恰一次被消费，失败标记恢复后不会丢 FIFO 或重复执行。`Host::ConsumeBridge` 当前为 private、完整 `DrawingController::Run` 要 GPU/HWND，故若要求全链**无 HWND**绿测，需抽出窄的生产控制服务 helper/注入 seam；不能用只模拟一套旁路调度逻辑的单测冒充已覆盖 Host。

**窗口关闭复验界限。** `CloseProgram` 与 `WindowService::Submit` 的实际 owner-thread 卡住必须用受限隐藏窗口或现场栈，纯无 HWND 无法证明 USER32 future.get 退路。可以把“发布进程关闭意图/后续尝试隐藏”的调度提成生产窄 helper，并在无 HWND 回调假件中让 hide 永不完成，断言退出信号/状态仍可观察；这只证明控制顺序。仍需隐藏窗口故障注入一次 overlay owner 不处理命令、一次 setting owner 不处理命令，确保不会在 HideAll 或 `StopAndJoin` 无界等待，并核旧可见 Drawpad 的输入隔离/进程退场。真实用户进程与配置不得用于此注入。

## 最小修补合同（供主审安排，本文未实施）

1. 控制 marker 入队失败不能把已接受 bridge/canvas 命令遗落：唤醒 generation 本身需让消费线程检查 pending 控制工作，或保留可重试原子标志；同一绘制线程串行 pump，保持 scene-stamped Clear/Workspace/Presentation 和最终 exit barrier 的 FIFO。失败时记录低频 `control_wake_enqueue_failed` 及队列/活动 contact 摘要；不要在 RTS callback 同步做磁盘/GPU 工作。
2. 退出不能在 `SetOffSignal` 之前无界等 Window owner：先建立只增的 close intent 并阻止重显，再按产品政策有界等待双窗隐藏/读回和 capture 释放。若 owner 不应答，必须报告具体 owner/thread/命令并走经设计的退场路径；不能把 `WS_EX_TRANSPARENT` 当桌面穿透保证，也不能让硬超时丢弃已接受 UInk 保存。现有规范 `errors-logging-and-resources.md:112-155` 要求“先同步隐藏再后台清理”，与卡住 owner 的场景冲突；调整时应显式更新该异常退路合同，而不是默默改正常视觉顺序。
3. 活动 contact 与画布命令之间增加可观测的 `activeCount/oldestQpc/terminalPending/admissionBlocked` 低频快照及退出阶段边沿；正常笔未 Up 时仍保留原命令顺序和笔迹，只有在 RTS shutdown/已知终态或明确故障 containment 时做安全封口。不能为让 Clear 立即生效而直接清空 active，不能把 fatal 后未持久化接触报成已保存。

复查命令：`rg -n 'PublishControlWake|AcknowledgeControlWake|StopWithFinalCommand|exitAutoSaveCondition.wait|processCanvasCommands|active.empty' Inkeys/Inkeys/Drawing/Draw3`；`rg -n 'CloseProgram|HideAllUserWindows|future|get\(|SetOffSignal|StopProduct|CloseAndDrain' Inkeys`。静态结论不替代线程栈、实际输入来源、presenter、Win7/Office/驱动与授权 GUI 验收。
